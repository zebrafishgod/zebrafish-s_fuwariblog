## 3.1 进程理论

### 3.1.1 并发与并行

在走进程之前，先分清两个核心概念。

- **并发（concurrency）**：**看起来像同时运行**就叫并发。比如一个人做三个任务，A 干一秒、B 干一秒、C 干一秒，再回到 A……感觉三个任务在同时推进，其实只有一个人在干。**单核的计算机就能实现并发**。
- **并行（parallelism）**：**真正意义上的同时执行**，必须一个人干一个任务。**必须有多核**。

并行本来就是同时执行，所以**并行也可以说是并发**。但反过来不成立：单核可以实现并发，不能实现并行。

这里说的"核"指 CPU 核心。一个 CPU 里往往有多个核，现在先假设单核只有一个核。

### 3.1.2 单道（串行）与多道技术

**单道**又称**串行**。要执行任务 A 和任务 B，先把 A 的代码读入内存，CPU 执行，交给输出设备输出；然后 B 才能读入内存、执行、输出。B 必须等 A 完全执行完毕才能开始。

```text
时间 →
任务A: [读入][CPU执行][输出]
任务B:                      [读入][CPU执行][输出]
```

用代码模拟一下串行：

```python
import time


def task(name):
    print(f"{name} 开始")
    time.sleep(1)
    print(f"{name} 结束")


start = time.time()
task("任务A")
task("任务B")
print(f"串行总耗时：{time.time() - start:.1f}s")
# 输出: 串行总耗时：2.0s
```

**多道技术的做法是：让 CPU 一刻都不停。** 先把任务 A 的代码从硬盘读入内存，CPU 从内存取指令运行。注意此时硬盘是空闲的，于是趁机把任务 B 的代码读入内存。A 执行完进入输出过程时，CPU 又闲下来了，就瞬间切换，立即从内存取出 B 的指令运行。

```text
时间 →
任务A: [读入][CPU执行A][输出A]
任务B:       [读入B]   [CPU执行B][输出B]
```

假设 A、B 各需 10 秒，串行要 20 秒，多道明显更短——**节省了多个程序运行的总耗时**。多道技术允许**多个程序同时进入内存，由 CPU 交替执行**：一个程序因 I/O 请求暂停时，CPU 立即运行另一个程序。

CPU 从 A 切到 B，再回到 A 时应接着上次的位置继续，所以切换时要**保存状态**。

> **多道技术的核心 = 切换 + 保存状态**

也正因为有了多道技术，计算机才**第一次出现了操作系统的概念**。

:::note[补充]
教科书里常把多道技术概括为"空间上的复用"（内存同时存放多个程序、彼此隔离）与"时间上的复用"（多个程序轮流使用 CPU）。
:::

### 3.1.3 CPU 切换的两种情况

情况一：**程序遇到 I/O 操作时，操作系统会剥夺它的 CPU 执行权限。**

比如程序执行 `open` 打开文件，这个过程 CPU 并没有工作，操作系统就把 CPU 拿去执行其他程序，等 I/O 完成后把 CPU 调回来。这样**既提高了 CPU 利用率，又不影响程序本身的执行效率**——原来这个程序需要 10 秒，现在还是 10 秒，只是利用了中间 CPU 空闲的时间。

情况二：**程序长时间占用 CPU 时，操作系统也会剥夺它的 CPU 执行权限。**

假设单核计算机上打开了一个游戏，它需要 CPU 不间断工作 10 分钟；期间又点开了 PyCharm、Typora、微信。如果游戏一直占着 CPU，其他程序就没法执行。所以操作系统一看某个任务占用 CPU 太久，就从中掐断，把 CPU 拿去执行一下 PyCharm、Typora、微信，再回来执行游戏。

但这样一来，游戏的耗时变成"10 分钟 + 中间切去执行其他任务的时间"，所以**第二种情况其实降低了该程序本身的运行效率**。

记住多道技术两句话：**切换 + 保存状态**；**遇到 I/O 会切换，长时间占用 CPU 也会切换**。

### 3.1.4 程序与进程

先分清程序和进程：

| | 程序（program） | 进程（process） |
|---|---|---|
| 本质 | 存在硬盘上的一堆代码 | 表示程序**正在执行的过程** |
| 状态 | **死的** | **活的** |

微信本来只是硬盘上的一段代码；打开后代码从硬盘加载到内存，我们可以使用它的各种功能，微信就"活"了。有了"进程"这个词，就不用说"内存里有一个微信程序正在运行"，直接说"微信进程""PyCharm 进程"，描述起来更方便。

```python
import os

print("当前进程号 PID：", os.getpid())
# 输出: 当前进程号 PID：12345   （每次不同）
```

同一个 `.py` 文件运行两次，就是两个进程，进程号不同。

### 3.1.5 进程调度算法

目的是实现并发，让 CPU 交替执行多个进程。内存里这么多进程，CPU 先执行谁、怎么切换？这要按一定规则来，即**进程调度**。调度算法是一步步演化过来的。

**1. 先来先服务调度算法**：哪个进程先来就先执行哪个。

问题：先来的需要 3 小时、后来的只需 3 秒，后者就要等 3 小时。**对长作业友好，对短作业不友好**。

**2. 短作业优先调度算法**：短作业先执行。

问题：**对短作业友好，对长作业不友好**——内存里排了 100 个短作业、1 个长作业，长作业只能等到最后。

**3. 时间片轮转法 + 多级反馈队列**：前两种都不合理，于是有了这种方式。

- **时间片**：把时间切成很多份，每一份就是一个时间片
- 操作系统给第一级队列里的每个进程分配一个时间片，一个时间片内没结束的进程，就被"请到楼下"放进**下一级队列**；CPU 执行完第一级队列后再执行下一级队列，还没结束就继续往下放
- **越往下，说明任务耗时越长，优先级也越低**。比如 CPU 正在执行下层某个任务，用户打开了微信，微信进入第一级队列，操作系统会让 CPU 立刻停下当前任务去执行微信——用户希望微信马上打开。下层都是耗时长的任务，回头先处理一下短任务，对它们影响不大
- 一个时间片非常短（毫秒、微秒级别），我们感知不到切换，所以感觉所有程序都在同时运行

```text
第1级队列（优先级最高）: [P1][P2][P3]  ← 新进程从这里进入
        ↓ 一个时间片内没结束
第2级队列:               [P1][P3]
        ↓ 还没结束
第3级队列（优先级最低）:  [P3]
```

:::note[补充]
Linux 中还可以给某个任务一次分配多个时间片，了解即可。
:::

### 3.1.6 进程三状态图

三状态图很好地诠释了一个程序经历的阶段：

```text
  双击程序/提交任务
         ↓ （从硬盘加载到内存）
     ┌──────┐   进程调度    ┌──────┐   执行完毕
     │ 就绪 │ ───────────→ │ 运行 │ ──────────→ 释放资源、退出
     └──────┘ ←─────────── └──────┘
        ↑    时间片用完       │
        │  （既没结束也没IO）  │ 遇到 I/O
        │                     ↓
        │     I/O 完成     ┌──────┐
        └──────────────── │ 阻塞 │
                          └──────┘
```

状态转换说明：

- 用户双击程序或提交任务，程序从硬盘加载到内存。**所有程序要想被执行，必须先经历就绪态**——先准备好，等待 CPU 执行
- 就绪态之后进入**进程调度**，进入**运行态**
- 运行中可能出现几种情况：
  1. 程序执行完了，立刻释放相应资源并退出
  2. 遇到 **I/O 操作**——读文件、写文件、发网络请求、`input` 等待用户输入、`time.sleep`、`print` 等。I/O 不需要 CPU，操作系统会把 CPU 拿走去执行其他时间片，当前程序进入**阻塞态**；I/O 完成（文件读写完毕、收到用户输入、sleep 时间到、print 打印完成）后结束阻塞，**但不会立刻进入运行态，而是回到就绪态排队**
  3. 分配的时间片用完了，程序既没结束也没有 I/O，就直接从运行态回到**就绪态**排队，等 CPU 下次来执行

**类比**：排队做核酸，终于轮到你，突然发现手机没拿，回家拿完手机回来，原来的位置还是你的吗？不是，得去后面重新排队。阻塞结束后也一样，要重新去就绪态排队。

用一段代码对照状态变化：

```python
import time              # 程序加载到内存 → 就绪态 → 调度后运行态

a = 1                    # 运行态
b = a + 1                # 运行态
name = input("请输入：")  # 等待用户输入 → 阻塞态；输入完成 → 就绪态 → 运行态
time.sleep(1)            # sleep → 阻塞态；时间到 → 就绪态 → 运行态
print(name, b)           # print 也是 I/O → 阻塞态；完成 → 就绪态 → 运行态
# 运行态发现没有代码了 → 释放该进程所有资源，程序终止
```

### 3.1.7 同步与异步

接下来是两对以后会经常遇到的重要概念，先记住它们的分类：

- **同步和异步**：描述的是**任务的提交方式**
- **阻塞和非阻塞**：描述的是**进程的运行状态**

**同步（synchronous）**：任务提交之后，**原地等待**任务的返回结果，等待过程中不做任何事。

**类比**：老板让你写一篇讲话稿（提交了一个任务），然后他就一直站在你面前什么都不干；你忙了大半天其他事，又花半天写完，老板整整等了一天才拿到讲话稿。

**异步（asynchronous）**：任务提交之后，**不在原地等待**，直接去做其他事。

**类比**：老板把任务交给你就去忙自己的了，你写完后主动告诉老板并交给他。

异步提交后人走了，结果怎么拿？就像你写完会主动交给老板一样，程序中任务的返回结果由**异步回调机制**自动处理：异步提交的任务只要有了返回结果，就会被自动拿到并处理。这里提交的任务通常是**一段代码或一个函数**。

```python
import time


def func():
    print("任务开始")
    time.sleep(5)
    print("任务执行完毕")


func()          # 调用函数 = 提交任务，这是同步调用：原地等 func 执行完
print("hello")  # 5 秒后才会打印
# 输出:
# 任务开始
# 任务执行完毕   （5 秒后）
# hello
```

调用 `func()` 是同步调用：先打印"任务开始"，睡 5 秒，打印"任务执行完毕"，拿到结果后才往下打印 `hello`。如果是异步调用，任务提交后立刻往后执行，会马上打印 `hello`，根本不用等 `func` 执行完。异步怎么写、回调函数怎么写，后面讲线程时再展开。

:::note[补充：先睹为快]
用线程就能实现异步提交（后续章节详讲）：
```text
import threading
import time

def func():
    print("任务开始")
    time.sleep(1)
    print("任务执行完毕")

t = threading.Thread(target=func)
t.start()       # 异步提交：不等 func 执行完
print("hello")  # 会紧接着"任务开始"立即打印
t.join()
```
:::

### 3.1.8 阻塞与非阻塞

阻塞和非阻塞描述的是**进程的运行状态**，其实前面已经见过了：

- **阻塞（blocking）**：就是三状态图中的**阻塞态**
- **非阻塞（non-blocking）**：就是三状态图中的**就绪态和运行态**

以后常会听到两对概念的组合：同步阻塞、同步非阻塞、异步阻塞、异步非阻塞。其中**最高效的是异步非阻塞**：

- 异步：任务提交后不原地等待，代码可以继续往下执行，效率上去了
- 非阻塞：程序不会进入阻塞态，永远在就绪态和运行态之间切换

这样无论是代码的执行效率还是 CPU 的利用率都比较高。现在比较厉害的一些框架都支持异步非阻塞，看到"异步非阻塞"，就应该知道这个框架速度一定很快。

写程序最理想的状态，就是让代码**永远在就绪态和运行态之间切换，没有一点阻塞**，这样代码被 CPU 执行的时间间隔短，运行效率自然高。当然这是理想状态，大部分程序都有阻塞——比如打开 PyCharm 不做任何操作，它就一直停在那个页面等待用户操作，这就是阻塞态。

:::note[补充]
socket 的 `setblocking(False)` 可把套接字设为非阻塞模式，后续章节会详细展开。
:::

## 3.2 multiprocessing 多进程编程

并发编程的理论部分讲完了，接下来看怎么创建进程。

### 3.2.1 创建进程的模块选择

创建进程最简单的方式是**双击应用程序图标**：双击 PyCharm、微信，就是让操作系统把程序代码从硬盘加载到内存，由 CPU 执行，创建出 PyCharm 进程、微信进程。这里主要讲**用代码创建进程**。

用代码创建进程和创建线程（thread，后面再讲）的代码基本一样：开发者在设计操作进程和操作线程的模块时遵循了同一套标准，也就是前面讲过的**鸭子类型**（duck typing）。掌握一种，另一种自然就会了。

Python 中创建进程的模块有好几个：

| 模块 | 说明 |
|---|---|
| `os.fork` | 依赖 Linux（UNIX）的 fork 系统调用，**Windows 没有 fork 系统调用，不支持**；用起来也不方便，不讲 |
| `subprocess` | 主要做运维时用来执行终端命令，功能不多 |
| `multiprocessing` | **本课程主要使用的模块** |

### 3.2.2 创建进程方式一：target 参数

右键运行一个 Python 文件时，内存里会开辟一块空间放这段代码，它就是一个进程，称为**主进程**；在它的基础上通过代码创建的进程称为**子进程**。

用 `multiprocessing` 创建进程，**两行代码**就够了：

1. `p = Process(target=func, args=(...))`：`Process` 是一个类，`target` 指定把谁作为子进程的任务来执行；函数需要的参数通过 `args` 以**元组**传入——**元组只有一个值时后面要加逗号**；函数没有参数就不用传 `args`。这一步只是得到一个**进程操作对象**。
2. `p.start()`：告诉操作系统，让操作系统帮我们真正创建一个进程。

```python
from multiprocessing import Process
import time


def func(name):
    print(f"{name}任务开始")
    time.sleep(3)
    print(f"{name}任务执行完毕")


if __name__ == "__main__":       # Windows 下必须写，原因见下一小节
    p = Process(target=func, args=("写讲话稿",))  # 只有一个参数，别忘了逗号
    p.start()                    # 让操作系统创建子进程
    print("主进程")
    p.join()
# 输出:
# 主进程
# 写讲话稿任务开始
# 写讲话稿任务执行完毕   （3 秒后）
```

`p.start()` 执行后立刻往后走，打印了"主进程"，根本不等提交的任务的结果——这就是**异步提交任务**的效果。

### 3.2.3 Windows 下创建进程的注意事项

如果不写 `if __name__ == "__main__":`，直接把创建进程的两行代码写在顶层，Windows 上运行会报错。原因是不同系统创建子进程的方式不同：

- **Mac / Linux**：创建进程时，把任务对应的代码和当前进程的数据集（变量等）**全部拷贝一份**，在子进程里执行任务，没有问题
- **Windows**：不是直接拷贝，而是**以类似导入模块的方式，在子进程里导入当前这个 Python 文件**。导入模块会把模块代码执行一遍，于是创建进程的代码又被执行，又以导入方式创建进程……进入**没有结束条件的"递归"**，这是非常致命的问题，Python 会直接报错

解决办法：只想在右键运行时执行、不想在被导入时执行的代码，放进 `if __name__ == "__main__":`。第一次右键运行时会走 `__main__` 下的代码创建进程；子进程把文件作为模块导入时不会再走 `__main__`，只执行前面的代码——这样子进程里也有了函数和其他变量。Windows 下的报错信息里其实也会提示你写这一句。

虽然只有 Windows 有这个问题，但为了代码更通用，**养成习惯：创建进程的代码都写在 `if __name__ == "__main__":` 里**。

```python
from multiprocessing import Process


def task():
    print("子进程执行")


print("这一行在 Windows 下会被子进程导入时再执行一次")

if __name__ == "__main__":   # 子进程导入本文件时 __name__ 不是 "__main__"，不会再次创建进程
    p = Process(target=task)
    p.start()
```

运行之后，内存中开辟**两块内存空间**，主进程运行主进程的代码，子进程运行子进程的代码，**互不干涉**；单核 CPU 下是并发效果，多核 CPU 下是并行效果。`p.start()` 可以理解为异步提交了一个任务，任务可以是函数，也可以是方法。

:::note[补充]
上面说的"拷贝"对应启动方式 `fork`，"导入"对应 `spawn`。从 Python 3.8 起 macOS 默认也改用 `spawn`，可用 `multiprocessing.get_start_method()` 查看。
:::

### 3.2.4 创建进程方式二：继承 Process

第二种方式是**面向对象**的写法：写一个类继承 `Process`，类里**必须定义 `run` 方法**——和 `socketserver` 一样，用别人的模块就得按别人的规矩来。`p.start()` 后，子进程会执行 `run` 方法。

如果想给 `run` 传参，不能直接传，只能在实例化类时传；传进去的参数交给 `__init__`，所以要**重写 `__init__`**，并且**不要忘了调用父类的 `__init__`**，再把参数存到 `self` 上供 `run` 使用。

```python
from multiprocessing import Process
import time


class MyProcess(Process):
    def __init__(self, name):
        super().__init__()          # 必须调用父类的 __init__
        self.task_name = name

    def run(self):                  # 子进程要执行的代码
        print(f"{self.task_name}任务开始")
        time.sleep(3)
        print(f"{self.task_name}任务结束")


if __name__ == "__main__":
    p = MyProcess("约会")
    p.start()
    print("主进程")
    p.join()
```

效果和方式一相同，但写法麻烦一点，**了解即可，一般用第一种**。

创建进程就是在内存中申请一块**独立的内存空间**，把要运行的代码放进去。多个进程的内存空间**彼此隔离**，进程之间的数据不能直接交互；要交互需借助其他工具或模块，后面再讲。

:::note[补充]
直接调用 `p.run()` 只是普通的方法调用，在主进程里执行，不会创建新进程。
:::

### 3.2.5 join 方法

`join` 的作用：**让主进程等待子进程运行结束之后再继续执行**。

前面的代码先打印"主进程"，再出现子进程的打印。现在的需求是让子进程的两句打印先执行完，再打印"主进程"。

- **笨办法**：子进程要睡 3 秒，那让主进程 `time.sleep(4)`。看似解决了，实则不然——我们并不知道子进程要运行多久，这次处理大文件要 10 秒，下次处理小文件只要 2 秒，主进程该睡多久？不合理
- **同步调用**：不创建进程，直接调用函数。但现在讨论的是进程，不考虑
- **`p.join()`**：主进程停在这里，等子进程执行完毕才执行后面的代码，感觉像任务是同步提交的。子进程结束的一瞬间，"主进程"立刻被打印

**加深理解**：创建 3 个进程，分别睡 1、2、3 秒，依次 `join`，总共大约耗时多少？

```python
from multiprocessing import Process
import time


def func(name, n):
    print(f"{name}任务开始")
    time.sleep(n)
    print(f"{name}任务执行完毕")


if __name__ == "__main__":
    start = time.time()
    p1 = Process(target=func, args=("任务1", 1))
    p2 = Process(target=func, args=("任务2", 2))
    p3 = Process(target=func, args=("任务3", 3))
    p1.start()
    p2.start()
    p3.start()
    p1.join()
    p2.join()
    p3.join()
    print(f"总耗时：{time.time() - start:.1f}s")
# 输出: 总耗时：3.1s   （不是 6 秒）
```

答案是 3 秒多一点。三个进程几乎同时起来，各自运行、互不干涉。主进程执行 `p1.join()` 等 p1 结束时，p2、p3 也在运行；p1 结束时它们已经运行了 1 秒，再等 p2 结束时 p3 已运行了 2 秒，所以总耗时约 3 秒。

另外，打印顺序**不一定**是 1、2、3：`p.start()` 只是告诉操作系统帮我们创建进程，代码不能直接创建进程；操作系统先创建哪个后创建哪个是随机的，所以可能出现 1 3 2、2 1 3 等顺序。

:::warning[注意：join 的常见陷阱]
**`join` 不能放在创建进程的循环里**，否则变成串行：
```text
# 错误写法：join 放在循环里 → 变成串行，总耗时 6 秒多
for i in range(1, 4):
    p = Process(target=func, args=(f"任务{i}", i))
    p.start()
    p.join()     # 第一个进程结束后才进入下一次循环创建第二个进程
```
正确做法是先用列表收集进程对象，最后再循环列表执行 `join`：
```text
if __name__ == "__main__":
    p_list = []
    for i in range(1, 4):
        p = Process(target=func, args=(f"任务{i}", i))
        p.start()
        p_list.append(p)    # 先把三个进程都创建起来
    for p in p_list:
        p.join()            # 再统一等待，等待时其他进程也在运行
```
:::

:::note[补充]
`join(timeout)` 可以只等待指定秒数，超时后主进程继续往下走，子进程仍在运行。
:::

### 3.2.6 进程间数据隔离

进程之间内存是隔离的。验证一下：主进程全局定义 `a = 18`，子进程的函数里用 `global` 声明并改成 16，主进程最后打印 `a`。

```python
from multiprocessing import Process

a = 18


def func():
    global a
    a = 16          # 改的是子进程自己全局的 a


if __name__ == "__main__":
    p = Process(target=func)
    p.start()
    p.join()        # 等子进程执行完再打印，结果更严谨
    print(a)
# 输出: 18
```

不加 `join` 时也打印 18，但可能有人怀疑是子进程还没执行主进程就打印了，所以加上 `join` 等子进程执行完再打印——结果仍是 18，说明确实隔离。

**原因**：子进程起来时会复制一份数据集（变量），所以子进程的全局也有一个 `a = 18`，它修改的是**自己全局的 `a`**，对主进程没有任何影响。

```text
内存
┌──────────── 主进程 ────────────┐   ┌──────────── 子进程 ────────────┐
│ a = 18                        │   │ a = 18  →  a = 16             │
└───────────────────────────────┘   └───────────────────────────────┘
```

### 3.2.7 进程号与父进程号

一台计算机上运行着很多进程，为了方便区分和管理，操作系统给每个进程分配一个 **PID**（Process ID），即**进程号**。同一台计算机上不同进程的进程号**独一无二**，类似前面讲的端口号。

终端查看所有进程及其 PID：

| 系统 | 查看所有进程 | 按进程号过滤 |
|---|---|---|
| Mac / Linux | `ps aux` | `ps aux \| grep 进程号` |
| Windows | `tasklist` | `tasklist \| findstr 进程号` |

代码中获取进程号，常用 `os` 模块：

- `os.getpid()`：获取当前进程号
- `os.getppid()`：get parent pid，获取**父进程号**

```python
from multiprocessing import Process
import os


def task(name="子进程"):
    print(f"{name}：{os.getpid()}")
    print(f"{name}的父进程：{os.getppid()}")


if __name__ == "__main__":
    p = Process(target=task)   # 默认 name 就是"子进程"
    p.start()
    p.join()
    task("主进程")
# 示例输出（进程号每次不同）:
# 子进程：27380
# 子进程的父进程：42232
# 主进程：42232
# 主进程的父进程：3764     ← 运行本文件的编辑器进程
```

子进程的父进程就是主进程。那主进程的父进程是谁？当前这个 Python 文件是**编辑器**帮我们运行起来的，所以主进程的父进程就是编辑器进程。

除了 `os` 模块，也可以用 `current_process().pid` 获取当前进程号（`current_process` 翻译过来就是"当前进程"）：

```python
from multiprocessing import Process, current_process


def task():
    print(f"子进程号：{current_process().pid}")


if __name__ == "__main__":
    p = Process(target=task)
    p.start()
    p.join()
    print(f"主进程号：{current_process().pid}")
```

**另外两个方法**：

- `p.terminate()`：杀死该进程。终端里对应 Windows 的 `taskkill /F /PID 进程号`，相当于在任务管理器里右键结束程序；Mac / Linux 用 `kill -9 进程号`
- `p.is_alive()`：判断进程是否存活，返回布尔值。命名启示：返回布尔值的变量、函数或方法，以 `is_` 开头，见名知义

```python
from multiprocessing import Process
import time


def task():
    print("任务执行中")


if __name__ == "__main__":
    p = Process(target=task)
    p.start()
    p.terminate()        # 只是向操作系统发起杀进程的请求
    time.sleep(0.01)     # 稍微延时，给操作系统一点时间
    print(p.is_alive())
# 输出: False（不延时可能打印 True）
```

不加延时会打印 `True`：代码不能直接杀死进程，只能向操作系统发起调用，中间需要一定时间；而代码运行很快，发起调用后立刻打印 `is_alive()`，此时操作系统还没来得及杀死进程。稍微延时（如 0.01 秒，不够就加长）就变成 `False` 了。

### 3.2.8 僵尸进程与孤儿进程

这个知识点了解即可。

```python
from multiprocessing import Process
import time


def task():
    print("任务开始")
    time.sleep(3)
    print("任务结束")


if __name__ == "__main__":
    p = Process(target=task)
    p.start()
    print("主进程")   # 打印后主进程代码已执行完，但它会等子进程结束后才退出
```

打印完"主进程"后，主进程代码已经执行完毕，但它并没有结束，而是等子进程运行完才结束。两个进程不是互不干涉吗？为什么要等？

**僵尸进程（zombie process）**：顾名思义，进程死了还剩一具"尸体"。子进程结束后仍有一些资源占用——进程号、运行状态、运行时间等基本信息，要等**父进程通过系统调用回收**，可以理解为子进程死后需要父进程来"收尸"。除了 init 进程，**所有进程最后都会步入僵尸进程**，这是每个进程结束时都要经历的阶段。上面主进程不退出，就是在等子进程结束后回收它的资源。

- 正常情况下僵尸进程**没有危害**：主进程结束后会自动回收，或者等待子进程执行完毕后回收
- **有危害的情况**：子进程退出后父进程没有及时处理，而父进程代码又一直没运行完（比如父进程不停地创建子进程却不回收），僵尸进程就会一直占用资源和进程号。系统可用的进程号是有限的，大量僵尸进程会导致资源被过度占用，甚至没有可用进程号而无法创建新进程。开发时应尽量避免

**孤儿进程（orphan process）**：子进程还活着，**父进程意外死亡**（比如在终端里把父进程强制杀掉），没人给子进程收尸了，这时的子进程就是孤儿进程。出现孤儿进程也没关系，操作系统开设了一个"孤儿院"——**init 进程**，专门管理孤儿进程、回收它们的资源，可以理解为孤儿进程的"干爹"。

:::note[补充]
在 Linux 中，子进程已结束但父进程尚未回收时，用 `ps aux` 可以看到状态为 `Z`、标注 `<defunct>` 的僵尸进程。`multiprocessing` 在 `join()`、`is_alive()`、创建新进程或主进程退出时会自动回收已结束的子进程。
:::

### 3.2.9 守护进程

了解运维的话会知道，那些在后台默认运行的服务称为**守护进程（daemon process）**，它们守护着操作系统：随操作系统启动而启动、随操作系统关闭而关闭（比如开机自启、关机才退出的软件）。

形象的比喻：古代君王死后，嫔妃、宫女、太监、军队都要陪葬——他们守护君王，君王死了，守护的人也不能活。**我这个进程死了，你也得跟着死**，这就是守护进程。

```python
from multiprocessing import Process
import time


def task(name):
    print(f"{name}还活着", flush=True)
    time.sleep(3)
    print(f"{name}正常死亡", flush=True)


if __name__ == "__main__":
    p = Process(target=task, args=("苏妲己",))
    # 也可以用关键字传参：Process(target=task, kwargs={"name": "苏妲己"})
    p.daemon = True      # 设为守护进程，必须写在 start() 之前
    p.start()
    time.sleep(1)
    print("纣王驾崩了", flush=True)
# 输出:
# 苏妲己还活着
# 纣王驾崩了          （苏妲己随之陪葬，不会打印"正常死亡"）
```

关键点：

- 不设守护进程：纣王都驾崩了，苏妲己还活得好好的，最后才"正常死亡"
- 把 `p.daemon = True` 写在 `start()` **后面**会报错，报错信息大意是 `process has already started`（进程已经启动了），反过来说就是**要在进程启动之前设置守护进程**
- 放到 `start()` 前面、主进程不睡：`start` 刚让操作系统去创建进程，下一行纣王就驾崩了，苏妲己根本没机会活过来，什么都不打印
- 驾崩前 `time.sleep(1)`：苏妲己先是存活状态，1 秒后纣王驾崩，她直接陪葬，活不到正常死亡那一步

记住这一行代码 `p.daemon = True` 即可。

:::warning[注意]
- 守护进程内不能再创建子进程，否则报 `AssertionError: daemonic processes are not allowed to have children`。
- 打印语句最好带 `flush=True`。守护进程被强制结束时不保证把缓冲区里的内容输出，加了 `flush` 才能稳定看到"苏妲己还活着"这一行。
- 以后项目跑在服务器上，报错可能有几百上千行，要慢慢学会自己看报错信息：抓住错误类型和关键词，积累常用单词，以后看几个关键词就能定位问题。
:::

## 3.3 进程间通信

### 3.3.1 为什么进程之间不能直接通信

上一节验证过：进程的内存空间彼此隔离，主进程的变量子进程改不了，子进程的变量主进程也看不到。但很多场景下进程就是要交换数据，比如一个进程负责抓数据、另一个负责存数据。

要打破隔离，就需要专门的通信手段。进程间通信有个专业名词：**IPC 机制（Inter-Process Communication，进程间通信）**。Python 提供了几种方式：

| 方式 | 说明 |
|---|---|
| `Queue` 消息队列 | 第三方队列，一个进程存、另一个进程取，**推荐** |
| `Pipe` 管道 | 在两个进程之间建立通道，只有两个端点，只能两端通信 |
| `Manager` | 提供一个可共享的 dict/list 等对象，多进程都能访问 |

管道和队列很像，数据在里面**只有一份**：拿一个少一个，你拿走了别人就拿不到。前面用过的 `subprocess` 模块，执行终端命令的结果就是通过 `stdout`、`stderr` 管道传来的。

那用哪个？**用队列**。因为**队列 = 管道 + 锁**，比管道好用得多，后面也是队列用得多、管道用得少。用队列时没提到锁，是因为它底层已经帮我们做好了。

:::note[补充]
除消息队列外，`multiprocessing` 还提供 `Pipe`（默认双向管道）、`Value`/`Array`（共享内存）和 `Manager`（可共享 dict/list）等 IPC 手段。它们各有适用场景，需要多个进程共享同一个小字典或列表时 `Manager` 更方便。
:::

### 3.3.2 消息队列基础

队列的特点：**先进先出（FIFO）**；与之相对的堆栈是**后进先出（LIFO）**。Python 提供的队列可以在内存里维护一份数据，支持存取。

导入方式有两种：

```python
import queue                       # 方式一：使用时写 queue.Queue
from multiprocessing import Queue  # 方式二：直接导入类（本章使用）
```

创建队列：`q = Queue(maxsize)`。

- `maxsize`：队列最多同时存放的数据量
- 默认值 0 并不是不能存数据：点进源码可以看到 `maxsize <= 0` 时会改用 `SEM_VALUE_MAX`，一路点进去是 **32767**。测试用不到那么大，传个 6 即可

**存数据 `q.put(数据)`、取数据 `q.get()`**：`get` 不用传参数，因为队列先进先出，一定先取最先存进去的数据。

```python
from multiprocessing import Queue

q = Queue(6)         # 最多同时存 6 个数据
for item in "abcdef":
    q.put(item)      # 存满 6 个
v1 = q.get()
v2 = q.get()
print(v1, v2)
# 输出: a b（先进先出）
```

- **队列满了再 `put`**：程序**阻塞**，什么时候有位置了再继续往下走
- **队列空了再 `get`**：程序也**阻塞**，原地等数据，有数据了取走再往下执行

### 3.3.3 队列的六个常用方法

不想阻塞的话，还有带超时和不等待的版本：

- `q.put_nowait(数据)`：放数据时不等待，队列满了直接报错 `queue.Full`
- `q.put(数据, timeout=3)`：队列满时等待 3 秒，3 秒后还是满的也报 `queue.Full`
- `q.get_nowait()`：取数据时不等待，没数据直接报错 `queue.Empty`
- `q.get(timeout=3)`：没有数据就原地等 3 秒，还没有就报 `queue.Empty`

另外两个判断方法：

- `q.full()`：判断队列是否满
- `q.empty()`：判断队列是否空

```python
from multiprocessing import Queue
import queue      # 异常类 queue.Full / queue.Empty 定义在标准库 queue 中
import time

q = Queue(6)
print(q.full())          # 还没存
for item in "abcdef":
    q.put(item)
time.sleep(0.1)          # 等后台线程把数据送进管道
print(q.full())

try:
    q.put("g", timeout=3)    # 满了，等 3 秒后报错
except queue.Full:
    print("队列满了")

for _ in range(6):
    print(q.get())           # 依次取出 a b c d e f

try:
    q.get_nowait()           # 空了，不等待直接报错
except queue.Empty:
    print("队列空了")
print(q.empty())
# 输出:
# False
# True
# 队列满了
# a
# b
# c
# d
# e
# f
# 队列空了
# True
```

六个方法：`put`、`get`、`put_nowait`、`get_nowait`、`full`、`empty`。**注意后四个方法在多进程条件下可能不够准确**：比如这个进程 `put_nowait` 时队列满了直接报错，刚报完错，另一个进程就从队列里拿走了一个数据，队列其实已经不满了；`get_nowait` 也一样。这些极限情况要知道。

:::warning[注意]
`multiprocessing.Queue` 的 `put` 由后台线程把数据送进管道，所以刚 `put` 完立刻调用 `full()`/`empty()` 也可能有短暂偏差，往往需要配合短延时。另外 `qsize()` 在 macOS 上会抛 `NotImplementedError`。
:::

### 3.3.4 用队列实现 IPC

**1. 主进程与子进程通信**

```python
from multiprocessing import Process, Queue


def task1(q):
    q.put("宫保鸡丁")      # 子进程往队列里放数据


if __name__ == "__main__":
    q = Queue()
    p = Process(target=task1, args=(q,))
    p.start()
    print(q.get())
    p.join()
# 输出: 宫保鸡丁
```

这里其实**不需要 `p.join()`**：`get` 拿不到数据会在原地阻塞，什么时候拿到了再往下走。打印是在主进程做的，数据是子进程放的，这就实现了主进程和子进程的通信。

**2. 子进程与子进程通信**

```python
from multiprocessing import Process, Queue


def task1(q):
    q.put("宫保鸡丁")      # 子进程 1 放数据


def task2(q):
    print(q.get())         # 子进程 2 取数据


if __name__ == "__main__":
    q = Queue()
    p1 = Process(target=task1, args=(q,))
    p2 = Process(target=task2, args=(q,))
    p1.start()
    p2.start()
    p1.join()
    p2.join()
# 输出: 宫保鸡丁
```

原本进程之间数据隔离，现在通过队列打破了隔离。多个进程也一样，可以通过同一个队列存取数据来通信。

### 3.3.5 为什么要序列化

队列能跨进程传数据，还有一个关键原因：**放进队列的数据必须先被序列化（pickle）成字节流，再由另一个进程反序列化还原。**

- **进程之间不共享内存**，队列底层是一条管道，只能传字节流，所以必须把 Python 对象转成字节
- 能被 `pickle` 的对象才能通过队列传输。**函数、类、打开的文件句柄等不能被序列化**，放进队列会报错
- 在 Windows 上（`spawn` 启动方式），连传给子进程的任务函数本身也要能被 pickle，所以 `target` 必须是**模块顶层定义的函数**，不能是 `lambda` 或嵌套函数

正因为要序列化，子进程拿到的永远是一份**数据副本**，改副本不影响原对象——这和 3.2.6 讲的内存隔离是一回事。

:::warning[注意]
把对象放进队列再取出，拿到的是反序列化后的**新对象**，不是原来那个（`id` 会不同）。想共享同一个可变对象，得用 `Manager`。`Manager` 返回的代理对象可以跨进程共享，但每次访问都要经过网络/进程间代理，比队列慢。
:::

## 3.4 互斥锁与数据竞争

### 3.4.1 问题引入：抢票场景

逢年过节上 12306 抢票时的常见场景：

1. 查询车票时显示还有 10 个座位
2. 犹豫 2 秒后点击购买
3. 提示"无票"

**原因**：你查票时拿到的是那一刻的数据快照；在你查票之后、买票之前，别人可能已经把票买走。用网页访问数据时，返回的是**访问那个时间点**的数据；拿到之后别人还可以改它，本地不会自动显示修改后的数据，除非刷新、重新发请求。

```text
12:00:00  你：查询成都车票 → 服务器返回此刻状态（有票）
12:00:00  他：也查询成都车票
12:00:01  他：直接购买成功
12:00:02  你：点击购买 → 重新查询最新状态 → 已无票
```

:::note[补充]
**竞争条件（race condition）**：多个执行单元竞争同一资源，导致结果不确定。
:::

### 3.4.2 模拟查票与买票

用 JSON 文件模拟数据库。创建 `data/tickets.json`（**必须用双引号**）：

```json
{"ticket_num": 2}
```

**两个核心函数**：

- **查票 `search_ticket(name)`**：读取文件，用 `json.load(fp)` 转为字典并打印余票
- **买票 `buy_ticket(name)`**：重新查询最新车票信息 → 模拟网络延迟 → 判断有票就减 1 写回

```python
import json
import random
import time
from multiprocessing import Process


def search_ticket(name):
    with open(DB, "r", encoding="utf-8") as f:
        dic = json.load(f)  # f 是文件对象，用 load（不是 loads）
    print(f"用户{name}查询余票：{dic.get('ticket_num')}")


def buy_ticket(name):
    # 再查一次最新车票信息
    with open(DB, "r", encoding="utf-8") as f:
        dic = json.load(f)
    time.sleep(random.randint(1, 3))  # 模拟网络延迟
    # 判断有票就买
    if dic.get("ticket_num") > 0:
        dic["ticket_num"] -= 1
        with open(DB, "w", encoding="utf-8") as f:
            json.dump(dic, f)
        print(f"用户{name}买票成功")
    else:
        print(f"余票不足，用户{name}买票失败")
```

:::tip[技巧]
`json.load` 接收文件对象（参数名 `fp`），`json.loads` 接收字符串（参数名 `s`）。看参数提示即可区分。
:::

### 3.4.3 多进程并发导致数据错乱

模拟 8 个人同时抢票（创建 8 个进程）：

```python
def task(name):
    search_ticket(name)
    buy_ticket(name)


if __name__ == "__main__":
    with open(DB, "w", encoding="utf-8") as f:
        json.dump({"ticket_num": 2}, f)   # 重置余票为 2
    ps = [Process(target=task, args=(i,)) for i in range(1, 9)]
    for p in ps:
        p.start()
    for p in ps:
        p.join()
    with open(DB, "r", encoding="utf-8") as f:
        print("最终余票：", json.load(f)["ticket_num"])
# 输出（节选）:
# 用户1查询余票：2
# 用户2查询余票：2
# ...
# 用户1买票成功
# 用户2买票成功
# 用户3买票成功
# ...
# 最终余票： 1
```

**运行结果**：8 个人都查到余票 2 张，8 个人都买票成功，但文件里余票还剩 1 张！

**原因分析**：8 个进程几乎同时查询，都看到余票为 2；然后都进入 `if` 判断，都把余票从 2 减到 1 写回，最终只减了一次。

:::warning[注意]
**多个进程操作同一份数据时，会出现数据错乱问题。解决方法是加锁。**
:::

### 3.4.4 互斥锁解决方案

**锁的原理**：把并发变成串行，牺牲效率保证数据安全。

**加锁步骤**：

1. 从 `multiprocessing` 导入 `Lock`
2. 在主进程创建锁：`mutex = Lock()`（变量名习惯用 mutex，即互斥锁）
3. 把锁作为参数传给所有子进程
4. 在争抢数据的环节加锁：`mutex.acquire()` 抢锁，`mutex.release()` 释放锁

**类比**：一群人抢一个厕所，抢到后把门锁上，别人就进不来；用完把锁打开，其他人再来抢。如果厕所门没锁，很多人一起用一个马桶——全乱套了。

```python
from multiprocessing import Process, Lock


def task(name, mutex):
    search_ticket(name)    # 查票：可以并发
    mutex.acquire()        # 抢锁
    buy_ticket(name)       # 买票：串行执行
    mutex.release()        # 释放锁


if __name__ == "__main__":
    with open(DB, "w", encoding="utf-8") as f:
        json.dump({"ticket_num": 2}, f)   # 重置余票
    mutex = Lock()                        # 主进程生成一把锁
    ps = [Process(target=task, args=(i, mutex)) for i in range(1, 9)]
    for p in ps:
        p.start()
    for p in ps:
        p.join()
# 输出（节选）:
# 用户1查询余票：2
# ...（8 个人都查到 2 张）
# 用户1买票成功
# 用户2买票成功
# 余票不足，用户3买票失败
# ...
# 最终余票： 0
```

**运行效果**：只有 2 人买到票，数据安全得到保证；但速度明显变慢，因为买票环节被串行了。

:::warning[注意]
- **不要轻易加锁**：只在争抢数据的环节加，锁多了程序退化成单道，还容易造成死锁
- 锁必须在主进程创建并传给子进程（进程间内存隔离，各自 `Lock()` 得到的是不同的锁，起不到互斥作用）
- 忘记 `release()` 或临界区内抛异常未释放，会导致其他进程永久阻塞
:::

**更安全的写法**是改用 `with mutex:`，异常时也会自动释放：

```python
def task(name, mutex):
    search_ticket(name)
    with mutex:          # 等价于 acquire() ... release()
        buy_ticket(name)
```

**关键结论**：**锁把并发变成串行，牺牲效率保证数据安全。** 不管是互斥锁、行锁、表锁，原理都一样。

:::note[补充]
以后遇到多个人争抢同一份数据、要保证数据安全时，第一反应就是加锁。写项目时锁一般由框架封装好，很少自己写，但要知道它背后的逻辑。
:::

## 3.5 生产者消费者模型

### 3.5.1 模型概念

**生产者消费者模型**是一个经典的并发模型，包含三要素：

- **生产者（producer）**：生产/制造数据
- **消费者（consumer）**：消费/处理数据
- **媒介**：消息队列（生产者和消费者不直接交互）

**类比**：去饭店吃饭 = 厨师（生产者）→ 桌子（媒介）→ 顾客（消费者）。如果没有桌子，厨师只能站在后厨用铲子直接往顾客嘴里喂——显然不合理。也就是说，**生产者和消费者不直接交互，而是借助媒介**。

### 3.5.2 基础实现

生产者不停制造数据，每个厨师做 3 份，做菜随机延时后放入队列；消费者用 `while True` 不停从队列取数据，吃完随机延时。

```python
from multiprocessing import Process, Queue
import time
import random


def producer(name, food, q):
    for i in range(3):                       # 每个厨师做 3 份
        time.sleep(random.uniform(0.1, 0.3))  # 做菜需要时间
        print(f"{name}生产了{food}{i}", flush=True)
        q.put(f"{food}{i}")


def consumer(name, q):
    while True:
        food = q.get()
        time.sleep(random.uniform(0.1, 0.3))  # 吃也需要时间
        print(f"{name}吃了{food}", flush=True)


if __name__ == "__main__":
    q = Queue()                              # 先把"桌子"摆好：消息队列
    p1 = Process(target=producer, args=("中华小当家", "黄金炒饭", q))
    p2 = Process(target=producer, args=("神厨小福贵", "佛跳墙", q))
    c1 = Process(target=consumer, args=("八戒", q))
    c2 = Process(target=consumer, args=("悟空", q))
    p1.start(); p2.start(); c1.start(); c2.start()
```

生产快、消费慢就多加消费者。谁先吃、谁吃几个没有规律，谁吃得快谁就吃得多。

**问题**：数据都处理完后，程序却阻塞了。主进程只是开了几个进程不会阻塞，生产者只循环 3 次也会结束，那就只能是消费者——它卡在 `q.get()` 上，队列没数据了就在原地等待，因为它不知道后面还会不会有数据进来。

### 3.5.3 结束方式一：结束标志

程序什么时候应该结束？生产者生产完、消费者处理完，就应该结束。所以：

1. 主进程里 `p1.join()` + `p2.join()`，等所有生产者生产完毕
2. 此时所有数据都已在队列里，再往队列放一个**特殊的结束标志**，比如 `"结束"`。队列先进先出，它一定排在所有数据的末尾
3. 消费者判断取到标志就 `break`，跳出循环结束运行
4. **有几个消费者就放几个标志**（队列数据取走即消失）

:::warning[注意]
不能在生产者函数末尾放标志：如果一个生产者快、一个慢，快的先结束放入的标志并不在所有数据末尾，会导致某个消费者提前退出，剩余数据由更少的消费者处理。
:::

```python
def consumer(name, q):
    while True:
        food = q.get()
        if food == "结束":                   # 拿到结束标志就退出
            break
        time.sleep(random.uniform(0.1, 0.3))
        print(f"{name}吃了{food}", flush=True)


if __name__ == "__main__":
    q = Queue()
    p1 = Process(target=producer, args=("中华小当家", "黄金炒饭", q))
    p2 = Process(target=producer, args=("神厨小福贵", "佛跳墙", q))
    c1 = Process(target=consumer, args=("八戒", q))
    c2 = Process(target=consumer, args=("悟空", q))
    p1.start(); p2.start(); c1.start(); c2.start()
    p1.join(); p2.join()                     # 等所有生产者生产完毕
    q.put("结束")                            # 有几个消费者，就放几个结束标志
    q.put("结束")
    c1.join(); c2.join()
    print("全部处理完毕")
# 输出（节选，顺序不固定）:
# 中华小当家生产了黄金炒饭0
# 神厨小福贵生产了佛跳墙0
# ...
# 八戒吃了黄金炒饭2
# 全部处理完毕
```

如果有 100 个消费者，就得放 100 个结束标志，比较麻烦。可以用 for 循环按消费者个数添加，但还有更好的方法，见下一节。

### 3.5.4 结束方式二：JoinableQueue + 守护进程

另一个方法是导入 **`JoinableQueue`**：`join` 是等待（像 `p.join()` 等待子进程结束），`able` 是"能够"，合起来就是"**能够等待的队列**"。它的用法和 `Queue` 一模一样，只是多了两个方法：

- `q.task_done()`：消费者每处理完一个数据调用一次，计数器减 1
- `q.join()`：主进程等待队列中所有数据被处理完（计数器变为 0）

**原理**：

- 每 `put` 一个数据，计数器 +1
- 每调用一次 `task_done()`，计数器 -1
- `q.join()` 阻塞，直到计数器为 0

**为什么还要保留 `p1.join()`、`p2.join()`？** 防止消费快、生产慢时队列中途被处理空，计数器提前变 0，导致 `q.join()` 提前通过。保留生产者的 `join`，就保证先等生产者把数据全部放进队列，再等计数器归零。

**为什么要守护进程？** `q.join()` 通过后数据已处理完，消费者还在 `while True` 里等新数据，没有退出条件，也就没有存在价值，应随主进程结束而结束——这正是上一节的**守护进程**。

```python
from multiprocessing import Process, JoinableQueue
import time
import random


def producer(name, food, q):
    for i in range(3):
        time.sleep(random.uniform(0.1, 0.3))
        print(f"{name}生产了{food}{i}", flush=True)
        q.put(f"{food}{i}")                  # 计数器 +1


def consumer(name, q):
    while True:
        food = q.get()
        time.sleep(random.uniform(0.1, 0.3))
        print(f"{name}吃了{food}", flush=True)
        q.task_done()                        # 处理完一个数据，计数器 -1


if __name__ == "__main__":
    q = JoinableQueue()
    p1 = Process(target=producer, args=("中华小当家", "黄金炒饭", q))
    p2 = Process(target=producer, args=("神厨小福贵", "佛跳墙", q))
    c1 = Process(target=consumer, args=("八戒", q))
    c2 = Process(target=consumer, args=("悟空", q))
    c1.daemon = True                         # 消费者设为守护进程
    c2.daemon = True
    p1.start(); p2.start(); c1.start(); c2.start()
    p1.join(); p2.join()                     # 先等生产者把数据全部放入
    q.join()                                 # 再等计数器变为 0（数据全部处理完）
    print("全部处理完毕")
# 输出（节选，顺序不固定）:
# 中华小当家生产了黄金炒饭0
# 神厨小福贵生产了佛跳墙0
# ...
# 八戒吃了佛跳墙2
# 全部处理完毕
```

**应用场景**：爬虫（爬取 HTML = 生产者，提取数据 = 消费者）、消息队列中间件（Celery、Kafka、RabbitMQ 本质上是生产者消费者模型的分布式版本）。

## 3.6 进程池预告

进程要频繁创建和销毁时，一个一个 `Process` 地开会比较浪费——创建进程要申请内存、拷贝代码，成本不低。解决办法是用**进程池（process pool）**：预先创建好一批进程放到池子里，有任务就交给池中的空闲进程处理，用完归还，不必反复创建销毁。

`multiprocessing` 提供的 `Pool` 就是进程池，常用方法有：

- `pool.apply(func, args)`：**同步**提交，一个任务做完再交下一个
- `pool.apply_async(func, args)`：**异步**提交，任务并发执行，返回结果对象
- `pool.close()`：不再接收新任务
- `pool.join()`：等待池中所有任务结束

进程池的详细用法放在下一章与多线程的 `concurrent.futures` 线程池一起讲。

## 本章小结

**进程理论**：

- 并发是看起来同时运行（单核即可），并行是真正同时运行（必须多核）；并行也是一种并发
- 单道即串行；多道技术的核心是**切换 + 保存状态**，目的是单核实现并发，并由此诞生了操作系统
- CPU 切换两种情况：遇到 I/O（提高利用率，不影响程序效率）、长时间占用 CPU（会降低该程序效率）
- 程序是硬盘上"死"的代码，进程是程序正在执行的"活"的过程
- 调度算法：先来先服务、短作业优先、时间片轮转 + 多级反馈队列（越往下耗时越长、优先级越低）
- 三状态：**就绪、运行、阻塞**；阻塞结束后先回到就绪态排队
- **同步/异步看任务提交方式**，**阻塞/非阻塞看进程运行状态**；异步非阻塞最高效

**multiprocessing 编程**：

- 创建进程主要用 `multiprocessing`；`os.fork` 在 Windows 上不可用
- 方式一：`Process(target=..., args=(...,))` + `start()`；方式二：继承 `Process` 重写 `run()`（传参需重写 `__init__` 并调用父类 `__init__`），一般用方式一
- `start()` 是异步提交；Windows 以导入模块方式创建子进程，必须把创建代码放进 `if __name__ == "__main__":`
- `join()` 让主进程等待子进程；多个子进程要"先全部 start 并存入列表，再统一 join"（join 别放进创建循环）
- 进程间内存相互隔离，子进程改的是自己那份数据
- `os.getpid()`、`os.getppid()`、`current_process().pid`；`terminate()` 杀进程、`is_alive()` 判断存活（系统调用需要时间）
- 僵尸进程：已结束未回收，父进程不回收时有危害；孤儿进程：父进程先死，由 init 进程收养
- 守护进程随主进程结束而结束，`p.daemon = True` 须在 `start()` 前设置

**进程间通信**：

- 进程内存隔离，通信要靠 **IPC**；队列 = 管道 + 锁，推荐用 `Queue`
- `Queue(maxsize)` 默认最大 32767；`put`/`get` 满/空时阻塞，`put_nowait`/`get_nowait` 及 `timeout` 参数抛 `queue.Full`/`queue.Empty`；`full()`/`empty()` 在多进程下不够准确
- 队列传输的数据要先**序列化**；函数、类、文件句柄不能放进队列
- 通过队列实现主进程与子进程、子进程间的通信，`get()` 拿不到数据会阻塞等待

**数据竞争与锁**：

- 多个进程操作同一份数据会出现**竞争条件**导致数据错乱；**互斥锁 `Lock`** 主进程创建、传给子进程，在争抢数据环节 `acquire()`/`release()`（或用 `with mutex:`）
- **锁把并发变成串行，牺牲效率保证数据安全**；不要轻易加锁，锁多了易死锁

**生产者消费者模型**：

- 生产者 + 消息队列（媒介）+ 消费者；两种结束方式：
  - 方式一：等生产者 `join()` 后按消费者个数放结束标志
  - 方式二：`JoinableQueue` + `task_done()` + `q.join()` + 消费者设为守护进程

1. ①遇到 I/O 操作；②长时间占用 CPU。第②种会降低该程序的效率（它的耗时要加上 CPU 去执行其他任务的时间）；第①种只是利用了 CPU 的空闲时间，不影响程序效率。

2. 不会，要先回到就绪态排队等待调度。就像排队做核酸轮到你时回家拿手机，回来后要到队尾重新排队。

```python
# 第3题
from multiprocessing import Process
import time


def task(n):
    time.sleep(n)
    print(f"任务{n}完成")


if __name__ == "__main__":
    start = time.time()
    p_list = []
    for i in range(1, 4):
        p = Process(target=task, args=(i,))
        p.start()
        p_list.append(p)
    for p in p_list:
        p.join()
    print("全部完成", f"{time.time() - start:.1f}s")
# 输出:
# 任务1完成
# 任务2完成
# 任务3完成
# 全部完成 3.1s
```

4. 打印 `0`。每个子进程修改的是自己内存空间里的 `n`，进程间数据隔离，主进程的 `n` 不受影响。

5. 代码不能直接杀死进程，只是向操作系统发起调用，操作系统处理需要时间；代码执行很快，打印时进程还没被杀死。加一点延时即可。

6. 普通子进程：主进程代码执行完后会等待子进程结束并回收；守护进程：主进程一结束，守护进程立即跟着结束。`daemon` 必须在 `start()` 之前设置，否则报错。

7. 数据错乱发生在修改数据（买票）的环节，查票只读不改可以并发。锁会把并发变成串行，只应该加在争抢数据的环节，加多了会降低效率甚至退化成单道。

8. `q.put(1)`：程序阻塞，等到有位置再继续；`q.put_nowait(1)`：直接报 `queue.Full`；`q.put(1, timeout=3)`：等待 3 秒后仍满报 `queue.Full`。

9. 放 3 个。队列数据取走一份就没了，每个消费者都要取到一个标志才能退出。如果在生产者末尾放，快的生产者先结束放入的标志并不在所有数据末尾，会导致某个消费者提前退出，剩余数据由更少的消费者处理。

```python
# 第10题
from multiprocessing import Process, JoinableQueue


def producer(q):
    for i in range(1, 6):
        q.put(i)


def consumer(name, q):
    while True:
        n = q.get()
        print(f"{name}: {n}^2 = {n * n}")
        q.task_done()


if __name__ == "__main__":
    q = JoinableQueue()
    p = Process(target=producer, args=(q,))
    cs = [Process(target=consumer, args=(f"c{i}", q)) for i in range(2)]
    for c in cs:
        c.daemon = True
    p.start()
    for c in cs:
        c.start()
    p.join()
    q.join()
    print("done")
# 输出（节选，顺序不固定）:
# c0: 1^2 = 1
# c1: 2^2 = 4
# ...
# done
```
