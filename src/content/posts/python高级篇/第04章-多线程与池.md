## 4.1 线程基础

### 4.1.1 线程与进程的关系

**进程是资源单位，线程是执行单位**。

- 进程相当于一块独立的内存空间，为线程提供各种资源
- 线程是真正干活的执行单元，CPU 执行的其实是进程里的线程
- 每创建一个进程，该进程里一定自带一个主线程，否则它没法干活

类比：操作系统是工厂，进程是车间，线程是流水线。车间本身不干活，它的作用是给流水线提供原材料、电力等资源；真正干活的是流水线。

**为什么明明有进程，还要有线程？** 对比两者的创建过程就清楚了：

| 对比 | 创建进程 | 创建线程 |
|---|---|---|
| 第一步 | 申请内存空间（消耗资源） | 不需要申请新的内存空间 |
| 第二步 | 拷贝代码（消耗资源） | 不需要拷贝代码 |
| 数据 | 进程间相互隔离，通信要用 IPC | 同一进程内的多个线程**数据共享** |

**创建线程所需的资源比创建进程小得多**，这是线程存在的第一个理由；第二个理由是同一进程内的线程天然共享数据，不用像进程那样做进程间通信。

举例：要开发一个"自动保存的编辑器"，需要三个功能——获取键盘输入、把输入内容实时显示到屏幕、自动保存到硬盘。这三个功能用线程实现最合适：它们处在同一个进程中，所需数据可以直接共享，也更节省资源；改用进程，不但要考虑进程间通信，还更耗资源。

### 4.1.2 创建线程：指定 target

`threading` 模块的操作和 `multiprocessing` 模块基本一致，两个模块的开发者有意这样设计，**学会一个，另一个也就会了**。

```python
from threading import Thread
import time

def task(name):
    print(f"{name} 任务开始")
    time.sleep(3)
    print(f"{name} 任务结束")

if __name__ == "__main__":
    t = Thread(target=task, args=("悟空",))   # 用法与 Process 一模一样
    t.start()
    print("主线程")
# 输出:
# 悟空 任务开始
# 主线程
# 悟空 任务结束
```

**线程与进程的关键区别在打印顺序上：**

- 进程版：总是"主进程"先打印。创建进程要申请内存空间、拷贝代码，很耗时间，代码只是向操作系统提交了一个创建请求，然后立刻往下执行
- 线程版："主线程"并不是最先打印的。`t.start()` 不用申请内存、不用拷贝代码，开销极低，可以说一执行线程就已经起来了

启动线程不强制写在 `if __name__ == "__main__":` 下，但为了和开进程的写法统一，习惯上照样写。

### 4.1.3 创建线程：继承 Thread

第二种方式是**继承**，与创建进程时的继承方式一模一样：继承 `Thread`，重写 `run` 方法。

`run` 方法由线程启动时自动触发，无法直接传参，只能通过对象属性传入。于是要重写 `__init__`；重写后父类的 `__init__` 就找不到了，而我们不知道父类里做了什么，**必须先 `super().__init__()` 重用父类的初始化**，再添加自己的属性。

```python
from threading import Thread
import time

class MyThread(Thread):
    def __init__(self, name):
        super().__init__()      # 重用父类的 __init__，必须调用
        self.name = name        # 通过对象属性把参数传给 run

    def run(self):              # 线程启动时自动调用
        print(f"{self.name} 任务开始")
        time.sleep(3)
        print(f"{self.name} 任务结束")

if __name__ == "__main__":
    t = MyThread("悟空")
    t.start()
    print("主线程")
# 输出:
# 悟空 任务开始
# 主线程
# 悟空 任务结束
```

:::note[补充]
`Thread` 自身就有 `name` 属性（线程名），`self.name = name` 实际是把线程名设成了"悟空"。若不想覆盖线程名，换个属性名如 `self.task_name` 即可。
:::

### 4.1.4 多线程实现 TCP 并发

回顾最原始的服务端：第一个客户端享受服务时，第二个客户端只能在外面等着，完全没有并发。

`accept` 相当于饭馆接客——接到一个客人后请进房间服务，门口就没人接客了。要把业务做大，就**门口专门用一个人接客，房间里找一堆人做服务**。

对应到代码：接客（`accept`）只要一个人；把做服务的通信循环提取到函数 `task(conn)` 里，每接到一个客户端就开一个线程去执行。

```python
# tcp_client.py —— 客户端，可同时运行多个
import socket
import time

c = socket.socket()
c.connect(("127.0.0.1", 8000))
while True:
    c.send(b"hello")
    data = c.recv(1024)
    print(data.decode("utf-8"))
    time.sleep(2)
```

```python
# tcp_server.py —— 多线程 TCP 并发服务端
import socket
from threading import Thread

def task(conn):
    """通信循环：为一个客户端服务"""
    while True:
        try:
            data = conn.recv(1024)
            if not data:                 # Linux/Mac 客户端断开会收空
                break
            print(data.decode("utf-8"))
            conn.send(data.upper())      # 给客户端回一个大写
        except ConnectionResetError:     # Windows 客户端异常断开会报错
            break
    conn.close()

if __name__ == "__main__":
    s = socket.socket()                  # 默认 AF_INET + SOCK_STREAM，即 TCP
    s.bind(("127.0.0.1", 8000))
    s.listen(5)
    while True:                          # 连接循环：门口只需一个人接客
        conn, addr = s.accept()
        t = Thread(target=task, args=(conn,))
        t.start()
```

先运行服务端，再运行多个客户端，它们可以同时享受服务，这就实现了 TCP 服务端的并发。把 `Thread` 换成 `Process` 同样可行。

这也正是 `socketserver.ThreadingTCPServer` 背后的原理。但"来一个客户端开一个线程"在客户端特别多时会耗尽资源，解决思路就是后面的"池"。

### 4.1.5 线程常用方法

**`join`：主线程等待子线程运行结束后再往下执行。**

```python
from threading import Thread
import time

def task(name):
    print(f"{name} 任务开始")
    time.sleep(3)
    print(f"{name} 任务结束")

if __name__ == "__main__":
    t = Thread(target=task, args=("悟空",))
    t.start()
    t.join()             # 主线程等待子线程运行结束
    print("主线程")      # 现在最后打印
```

**数据共享：同一进程里不同线程的数据是共享的。**

```python
from threading import Thread

age = 18

def task():
    global age       # 声明全局变量
    age = 16         # 子线程中修改

if __name__ == "__main__":
    t = Thread(target=task)
    t.start()
    t.join()
    print(age)       # 输出: 16（进程版这里仍是 18）
```

子线程把 `age` 改成 16，主线程打印出来也是 16，说明改的是同一个 `age`。

:::warning[注意]
不加 `join` 时，上面的打印可能是 18 也可能是 16——主线程不保证能看到子线程的修改。要稳定的结果就加 `t.join()`。
:::

**两个了解即可的方法：**

- `current_thread().name`：获取当前线程的名字。主线程叫 `MainThread`，子线程依次叫 `Thread-1`、`Thread-2`……
- `active_count()`：统计活跃的线程数量

```python
from threading import Thread, current_thread, active_count
import time

def task():
    print(current_thread().name)   # 新版形如 Thread-1 (task)
    time.sleep(1)                  # 不加延迟，线程跑得太快，统计时可能已结束

if __name__ == "__main__":
    t1 = Thread(target=task)
    t2 = Thread(target=task)
    t1.start()
    t2.start()
    print(current_thread().name)   # MainThread
    print("活跃的线程数量", active_count())   # 输出: 3（主线程 + 2 个子线程）
```

## 4.2 守护线程与线程安全

### 4.2.1 守护线程

**主线程会等待所有非守护子线程结束。**

```python
from threading import Thread
import time

def task(name):
    print(f"{name} 还活着")
    time.sleep(3)
    print(f"{name} 正常死亡")

if __name__ == "__main__":
    t = Thread(target=task, args=("大吉",))
    t.start()
    print("皇帝驾崩")
# 输出:
# 大吉 还活着
# 皇帝驾崩
# 大吉 正常死亡    ← 主线程代码已运行完，但等到这里才真正结束
```

为什么？进程里有主线程和子线程。如果主线程代码运行完毕就直接结束，就意味**整个进程结束了**；而子线程可能还在运行，它所需的资源要找进程拿，进程却被关闭了。所以**主线程运行完毕后不会立刻结束，要等所有非守护子线程运行完毕才结束**——主线程结束就意味着进程结束。

**守护线程**：和守护进程一样，"主线程死了，守护线程跟着陪葬"。在 `t.start()` 之前设置 `t.daemon = True`：

```python
from threading import Thread
import time

def task(name):
    print(f"{name} 还活着")
    time.sleep(3)
    print(f"{name} 正常死亡")

if __name__ == "__main__":
    t = Thread(target=task, args=("大吉",))
    t.daemon = True          # 设为守护线程，必须在 start() 之前
    t.start()
    print("皇帝驾崩")
# 输出:
# 大吉 还活着
# 皇帝驾崩               ← 没等到"正常死亡"，子线程就跟着结束了
```

:::warning[注意]
**是主线程"结束"之后守护线程才陪葬，而不是主线程"代码运行完毕"守护线程就陪葬。** 如果有非守护子线程还在运行，主线程会等待它们结束，这段时间里守护线程不会陪葬。
:::

一个容易错的例子：

```python
from threading import Thread
import time

def f1():
    print("任务1开始")
    time.sleep(1)
    print("任务1结束")

def f2():
    print("任务2开始")
    time.sleep(2)
    print("任务2结束")

if __name__ == "__main__":
    t1 = Thread(target=f1)
    t2 = Thread(target=f2)
    t1.daemon = True          # 只有 t1 是守护线程
    t1.start()
    t2.start()
    print("主线程")
# 输出:
# 任务1开始
# 任务2开始
# 主线程
# 任务1结束
# 任务2结束
```

分析：主线程代码运行完后要等所有非守护线程结束，t1 是守护线程不用等，**主线程等的是 t2**。在等 t2 的过程中主线程没结束，守护线程 t1 也就不会陪葬；1 秒后 t1 打印"任务1结束"，再过 1 秒 t2 打印"任务2结束"，最后主线程结束。所以全部内容都会打印。

如果让 t1 睡 3 秒，主线程等 t2 结束后就直接结束了，此时 t1 还没运行完，就会跟着陪葬，"任务1结束"不会被打印。

:::note[补充]
也可以用构造参数 `Thread(target=f1, daemon=True)` 设置；旧写法 `t.setDaemon(True)` 在 Python 3.10 起已弃用。
:::

### 4.2.2 线程互斥锁

同一进程内的多个线程数据共享，多个线程操作同一份数据时就可能出现数据错乱。仿照"抢票"：

```python
from threading import Thread
import time

num = 180

def task():
    global num
    tmp = num            # 获取车票数量
    time.sleep(0.05)     # 模拟网络延迟
    num = tmp - 1        # 卖出一张票

if __name__ == "__main__":
    l = []
    for i in range(180):
        t = Thread(target=task)
        t.start()
        l.append(t)
    for t in l:
        t.join()
    print(num)           # 输出: 179
```

为什么是 179 而不是 0？180 个线程起来后都先拿到 `num = 180`，然后都睡 0.05 秒，最后都执行 `180 - 1`。180 个线程卖出去了 180 张票，账面上却只减了 1。**加锁处理，把并发变成串行**：

```python
from threading import Thread, Lock
import time

num = 180
mutex = Lock()           # 线程间数据共享，锁放在全局，各线程直接就能拿到

def task():
    global num
    mutex.acquire()      # 抢锁
    tmp = num
    time.sleep(0.05)
    num = tmp - 1
    mutex.release()      # 释放锁

if __name__ == "__main__":
    l = []
    for i in range(180):
        t = Thread(target=task)
        t.start()
        l.append(t)
    for t in l:
        t.join()
    print(num)           # 输出: 0（串行执行，约 0.05×180 ≈ 9 秒）
```

加锁牺牲了效率，但保证了数据安全。加锁还有一种 `with` 写法，代码块执行完毕会自动调用 `mutex.release()`：

```python
def task():
    global num
    with mutex:              # 自动 acquire，代码块结束自动 release
        tmp = num
        time.sleep(0.05)
        num = tmp - 1
```

:::warning[注意]
线程场景请从 `threading` 导入 `Lock`。虽然从 `multiprocessing` 导入也能跑，但后者是基于操作系统信号量、面向进程设计的锁，开销更大。
:::

## 4.3 GIL 全局解释器锁

### 4.3.1 GIL 是什么

**GIL**，全称 **Global Interpreter Lock**，全局解释器锁。它的要点有三条：

- **GIL 是 CPython 解释器独有的特点，不是 Python 语言的特点**。Python 解释器有多个版本：CPython、Jython、PyPy 等
- GIL 是一把**互斥锁**，用来保护对 Python 对象的访问，**阻止同一个进程下的多个线程同时执行**
- 原因：**CPython 的内存管理不是线程安全的**（CPython's memory management is not thread-safe）

现在的计算机都是多核的，理论上多个 CPU 可以实现并行；但在 CPython 中，同一进程下的多个线程不能同时执行，有多个 CPU 也只能一次用一个。于是很多人会说"Python 不行，不能利用多核"——这种说法考虑得不够全面，4.4 节会说明什么时候该用多进程、什么时候多线程仍然有优势。

:::note[补充]
Python 3.13 起提供了实验性的 "free-threaded"（无 GIL）构建版本（PEP 703），需要单独安装 `python3.13t`；默认发行版仍然带 GIL。
:::

### 4.3.2 GIL 为什么存在

"内存管理"指的就是**垃圾回收机制**，它分三类：

- **引用计数**：内存中的值有变量名指向时引用计数加一，变量名销毁后减一
- **标记清除**：程序运行中发现内存占用较大时，会暂停当前程序，扫描内存，把从栈区无法访问到的值打上标记，统一清除，以释放大量内存
- **分代回收**：有些值存活周期很长，若每次都把所有值扫一遍很耗资源。于是把值分成几代：GC（garbage collection）巡逻时，多次扫描后依然存活的值放入下一代，越往后的代巡逻频率越低

```python
import sys

a = []
b = a
print(sys.getrefcount(a))   # 输出: 3（a、b，以及 getrefcount 的参数本身）
```

**垃圾回收为什么在多线程下不安全？反过来推导**：假设同一进程下的多个线程可以同时执行。

1. 一个进程里有多个线程，比如三个线程都执行 `age = 18; print(age)` 这段代码
2. 代码不能直接被 CPU 执行，必须先交给 **Python 解释器**，CPU 跟解释器打交道。每个进程下都有一个独立的解释器，用来解释该进程下的代码
3. 垃圾回收机制也是一个功能，它不是进程就是线程——它是一个线程，即**垃圾回收线程**，管理当前进程下的垃圾回收，它也要找解释器执行
4. 假设计算机有 4 个核，这些线程各拿一个 CPU 同时执行。就可能出现一种极限情况：线程 2 刚在内存中申请出 `18`，**还没来得及绑定变量名**，垃圾回收线程恰好来了，一看这个 18 没有引用计数，直接就把它回收了

线程操作 `a = 18` 时垃圾回收线程也来"凑热闹"，显然不安全。所以 CPython 在解释器上加了一把互斥锁 GIL：多个线程想运行就要先抢 GIL，谁抢到谁拿着解释器运行，其他线程（包括垃圾回收线程）只能在外面等着。这样线程操作 `a = 18` 时就不会被干扰；**线程遇到 IO 时会释放 CPU，GIL 也会自动释放**。

```text
进程
 ├─ 线程1 ─┐
 ├─ 线程2 ─┤
 ├─ 线程3 ─┼─→ 抢 GIL ─→ 拿到 GIL 的线程才能交给解释器执行
 └─ GC线程 ┘
```

**结论：**

1. GIL 导致同一进程下的多个线程**无法同时执行**，即无法利用多核能力
2. GIL 保证的是**解释器级别的数据安全**
3. 写代码时该怎么写就怎么写：多个线程抢同一份数据时**还是要自己加锁**，不用考虑 GIL

### 4.3.3 用代码验证 GIL 的存在

复制 4.2.2 的抢票代码，**去掉锁和延迟**运行：

```python
from threading import Thread

num = 180

def task():
    global num
    tmp = num
    num = tmp - 1        # 没有 IO，一个时间片内就跑完了

if __name__ == "__main__":
    l = []
    for i in range(180):
        t = Thread(target=task)
        t.start()
        l.append(t)
    for t in l:
        t.join()
    print(num)           # 输出: 0
```

结果变成了 0。这就能从侧面感受到 GIL 的存在：180 个线程并不是同时执行的，它们要去抢 GIL；第一个线程抢到 GIL 后瞬间完成了"取值减一"，结束并释放 GIL，下一个线程再来抢。GIL 看不见摸不着，但这个验证说明了它。

**那为什么加上延迟后又变成 179？** 每个线程抢到 GIL、拿到 `num` 后要睡 0.05 秒——**进入 IO 就会释放 GIL**。其他线程接着抢 GIL，也拿到 `num` 后释放……0.05 秒之内 180 个线程都抢到过一次 GIL、都拿到了 `num = 180`，最后都执行 `180 - 1`。网络延迟是没办法避免的，所以要让 `num` 正常从 180 减到 0，必须自己再加一把锁。

**加了自己的锁为什么就对了？** 180 个线程先抢 GIL，抢到后再抢我们自己的互斥锁，拿到 `num`，然后睡 0.05 秒——进入 IO 自动释放了 GIL，**但我们自己的锁并没有释放**。其他线程依次抢到 GIL 进来，执行到 `mutex.acquire()` 时发现锁还被第一个线程占着，只能卡住。绕了一圈后，GIL 回到第一个线程手里，它执行 `180 - 1` 后释放互斥锁；剩下的 179 个线程再抢 GIL、抢互斥锁……如此循环往复，**始终同一时刻操作 `num` 的线程只有一个**。

:::warning[注意]
不要把"去掉延迟后结果是 0"理解成 GIL 自动保证了数据安全。它只是因为这段代码执行太快，线程在一个时间片内就跑完了。CPython 会每隔一段时间（`sys.getswitchinterval()`，默认 5 毫秒）强制切换线程，计算量一大，"读-改-写"同样可能被打断。**GIL 不能代替自定义锁。**
:::

## 4.4 多进程 vs 多线程

### 4.4.1 何时用哪个

CPython 中同一进程下的多个线程无法利用多核，是不是多线程就没用了？要分情况：**单核 / 多核**，以及任务是**计算密集型 / IO 密集型**。

- **单核**不用考虑：本来就只有一个"人"在工作，多线程即便能利用多核，也没有多个核给它用；何况现在的计算机基本都是多核的
- **多核 + 计算密集型**（CPU 需要不停地工作，代码没有任何 IO）：假设有 10 个任务、每个 10 秒，计算机有 10 个核
  - 多进程：开 10 个进程，10 个 CPU 同时计算，总耗时约 10 秒多一点
  - 多线程：同一进程下的多个线程无法利用多核，总耗时约 100 秒
  - → **计算密集型用多进程**效率更高
- **多核 + IO 密集型**（任务频繁出现 IO 操作）：两者耗时差不多。多进程虽然能用多个 CPU，但大部分时间都在 IO，CPU 在 IO 时并不工作，10 个 CPU 都在"等"就没意义了；多线程虽然只有一个 CPU 干活，但可以来回切换（切换耗时完全可以忽略）。"你 10 个 CPU 在等，我 1 个 CPU 也在等"，而多线程更节省资源
  - → **IO 密集型用多线程**更有优势

所以多线程和多进程各有应用场景，不能单纯说多线程没用。

### 4.4.2 代码验证

先查看本机 CPU 核数：

```python
import os
print(os.cpu_count())   # 例如输出: 4
```

**计算密集型**：一直累加，完全没有 IO。

```python
from multiprocessing import Process
# from threading import Thread    # 多线程版
import time

def task():
    res = 0
    for i in range(10_000_000):   # 纯计算，没有 IO
        res += i

if __name__ == "__main__":
    l = []
    start = time.time()
    for i in range(4):            # 4 核 CPU，开 4 个
        p = Process(target=task)  # 改成 Thread(target=task) 即为多线程版
        p.start()
        l.append(p)
    for p in l:
        p.join()
    print("花费时间", round(time.time() - start, 2))
# 本机实测（16 核）: 多进程约 0.45 秒，多线程约 1.2 秒
```

**IO 密集型**：纯 IO。

```python
from threading import Thread
# from multiprocessing import Process   # 多进程版
import time

def task():
    time.sleep(1)                  # 纯 IO

if __name__ == "__main__":
    l = []
    start = time.time()
    for i in range(4000):          # 只开 4 个效果不明显
        t = Thread(target=task)
        t.start()
        l.append(t)
    for t in l:
        t.join()
    print("花费时间", time.time() - start)
# 本机实测: 4000 个线程约 1.5 秒；换成 4000 个进程则要十几秒
```

:::note[补充]
具体秒数和 CPU 核数、机器负载有关，重点是两者的量级差距：计算密集型多进程远快于多线程，IO 密集型多线程远快于多进程。
:::

**总结：**

- 多进程和多线程都有各自的优势。以后写项目时通常是**多进程下面再开多线程**，既能利用多进程使用多核的能力，又能利用多线程节省资源
- 我们开发的程序 **90% 以上是 IO 密集型**：服务端等待客户端连接、等待客户端输入、网络传输、网络延迟、文件读写、数据库读写，都是 IO。打开一个软件，只要用户不操作，CPU 就不用计算
- IO 密集型用多线程，即便不能利用多核、不能并行，也能提供**并发**能力，既节省资源又能实现并发；而且 IO 密集型任务也不需要太高的执行效率——有时效率高反而浪费资源
- 需要高效率、让 CPU 不停计算的场景才适合多进程，例如挖矿、训练人工智能、科学计算

## 4.5 死锁与递归锁

### 4.5.1 死锁

抢锁之后一定要释放锁，表面看一切正常。但即便"一个抢锁对应一个释放"，使用中也很容易出现一个奇怪的现象——**死锁**（deadlock）：整个程序阻塞住。

先实例化两把锁。注意它们是**两个不同的对象**：只要"类加括号"，就会实例化一个新对象。

```python
from threading import Thread, Lock, current_thread
import time

mutex1 = Lock()
mutex2 = Lock()        # 两把不同的锁

def task():
    # 第一段：先抢锁1，再抢锁2，然后释放锁2、释放锁1
    mutex1.acquire()
    print(current_thread().name, "抢到锁1")
    mutex2.acquire()
    print(current_thread().name, "抢到锁2")
    mutex2.release()
    mutex1.release()

    # 第二段：把顺序换一下，先抢锁2，再抢锁1
    mutex2.acquire()
    print(current_thread().name, "抢到锁2")
    time.sleep(1)      # 加一点延迟，结果更稳定，便于分析
    mutex1.acquire()
    print(current_thread().name, "抢到锁1")
    mutex1.release()
    mutex2.release()

if __name__ == "__main__":
    for i in range(8):
        t = Thread(target=task)
        t.start()
# 输出（之后程序永远卡住，需手动终止）:
# Thread-1 (task) 抢到锁1
# Thread-1 (task) 抢到锁2
# Thread-1 (task) 抢到锁2
# Thread-2 (task) 抢到锁1
```

**为什么会卡住？** 对照打印结果分析：

1. 线程 1 先起来，抢到锁 1；其他 7 个线程起来后只能在外面等着，一行代码都执行不了
2. 线程 1 抢锁 2——其他线程还卡在锁 1 处，所以线程 1 顺利抢到锁 2，打印后释放锁 2、释放锁 1
3. 线程 1 释放锁 1 的一瞬间，其他 7 个线程都去抢锁 1；与此同时线程 1 在抢锁 2，所以线程 1 再次顺利抢到锁 2，打印后**进入睡眠**
4. 剩下 7 个线程中肯定有一个（线程 2）抢到了锁 1，打印后开始抢锁 2——但此时锁 2 在线程 1 手上
5. 线程 1 睡醒后并不会立刻释放锁 2，而是去抢锁 1——可锁 1 在线程 2 手上

于是：**锁 2 在线程 1 手上，线程 1 等锁 1；锁 1 在线程 2 手上，线程 2 等锁 2**。它们都把自己锁在了自己的房间里，却都想在不开门的情况下拿到对方手上的锁，整个程序就"夯住"了。

:::warning[注意]
不要随意使用互斥锁，很容易造成死锁现象。而且死锁不一定出现在同一个函数里——比如把第二段代码提取到另一个函数（甚至另一个模块）中调用，结果一样会卡死。
:::

:::tip[技巧]
避免死锁的常用方法：所有线程**按相同顺序**获取多把锁；使用带超时的 `acquire(timeout=...)`；或使用下一节的递归锁。另外，同一线程对同一把普通 `Lock` 重复 `acquire` 也会把自己卡死。
:::

### 4.5.2 递归锁

**递归锁**（RLock，Reentrant Lock）：简单说就是**一个人可以重复地抢锁和释放锁**，类似递归。

- 内部有一个**计数器**：每 `acquire` 一次加 1，每 `release` 一次减 1
- 只要计数不为 0，其他人就抢不到这把锁
- 抢到锁的人可以继续 `acquire`，计数变成 2、3……；**抢多少次就要释放多少次**
- 递归锁**必须由抢到它的那个线程来释放**

**用法**：如果只是把 `Lock` 换成 `RLock`，得到的是**两把**递归锁，依然会死锁。想让 `mutex1` 和 `mutex2` 是同一把锁，最简单的办法是 `mutex1 = mutex2 = RLock()`——让两个变量名指向同一个对象的内存地址。

```python
from threading import Thread, RLock, current_thread
import time

mutex1 = mutex2 = RLock()   # 两个变量名指向同一把递归锁

def task():
    mutex1.acquire()                        # 计数 1
    print(current_thread().name, "抢到锁1")
    mutex2.acquire()                        # 同一把锁，同一线程再抢，计数 2
    print(current_thread().name, "抢到锁2")
    mutex2.release()                        # 计数 1
    mutex1.release()                        # 计数 0，其他线程才能抢

    mutex2.acquire()
    print(current_thread().name, "抢到锁2")
    time.sleep(1)
    mutex1.acquire()
    print(current_thread().name, "抢到锁1")
    mutex1.release()
    mutex2.release()

if __name__ == "__main__":
    for i in range(8):
        t = Thread(target=task)
        t.start()
# 程序不再卡住，可以正常结束
```

为什么不会死锁：线程 1 抢到锁 1 后计数为 1，其他人抢不到；再抢"锁 2"（其实是同一把锁）计数变成 2；释放两次计数归零。此时虽然所有人都可以抢，但线程 1 更快，又抢到"锁 2"，计数变 1，其他人还是进不来；它睡 1 秒，再抢一次计数变 2，释放两次归零，线程 1 全部结束。其他线程就这样重复这个过程，直到全部运行完毕。

除第一次肯定是线程 1 先抢到外，之后哪个线程先抢到锁是没有规律的。

## 4.6 同步工具

### 4.6.1 信号量 Semaphore

**信号量**（Semaphore）用来**控制同时访问特定资源的线程数量**，通常用于资源有明确访问数量限制的场景，简单说就是**限流**。比如数据库连接池：同时进行的连接数有上限，达到上限后，后面的线程只能等前面的释放。

类比：**停车场**。

- 互斥锁相当于停车场只有一个车位，停进一辆车，其他车就进不去了
- 信号量相当于停车场有多个车位，比如 5 个：进来一辆车，显示牌显示剩余车位 4 个；进满 5 辆车就显示 0 个，外面的车不能再进；出去一辆车剩余车位加 1

`Semaphore(value)` 中的 `value` 默认等于 1；`value < 0` 会抛 `ValueError`。

```python
from threading import Thread, Semaphore
import time
import random

sp = Semaphore(5)   # 给停车场开设 5 个车位

def task(name):
    sp.acquire()                        # 抢车位
    print(f"{name} 抢到车位")
    time.sleep(random.randint(3, 5))    # 停车 3~5 秒
    sp.release()                        # 车辆出场，释放车位

if __name__ == "__main__":
    for i in range(25):
        t = Thread(target=task, args=(f"宝马{i + 1}号",))
        t.start()
# 效果: 5 辆车同时进去，之后走几辆车就空出几个车位，才能再进几辆
```

:::note[补充]
`Semaphore(0)` 是合法的（初始没有车位，需要别人先 `release`）；`Semaphore` 同样支持 `with sp:` 写法自动获取和释放。
:::

### 4.6.2 Event 事件

主线程可以用 `join` 等待子线程运行完毕再继续，但**子线程与子线程之间无法用 join 互相等待**。要让一个子线程等另一个子线程发出信号再继续，就用 **Event 事件**。

`Event` 是一个类，直接实例化即可：

- `event.set()`：发射一个信号
- `event.wait()`：等待信号，没有信号就一直等；只要有人执行了 `event.set()`，立马往后走

模拟等公交车的场景：

```python
from threading import Thread, Event
import time

event = Event()

def bus():
    print("公交车即将到站")
    time.sleep(3)
    print("公交车到站了")
    event.set()                    # 司机开门：发信号，可以上车了

def passenger(name):
    print(f"{name} 正在等车")
    event.wait()                   # 等待信号，没等到就一直等
    print(f"{name} 上车出发")

if __name__ == "__main__":
    t = Thread(target=bus)         # 先让公交车跑起来
    t.start()
    for i in range(10):            # 等车的人可能有很多
        t = Thread(target=passenger, args=(f"乘客{i}",))
        t.start()
# 效果: 一开始车没到，所有人都在等车；3 秒后车到了，所有人都上车出发
```

:::note[补充]
`Event` 还有 `clear()`（把信号重置为未设置）和 `is_set()`（查看是否已设置），`wait(timeout=...)` 可以设置最长等待时间。
:::

### 4.6.3 Queue 补充

不同进程间通信需要用队列作为中转；同一进程下的多个线程数据是共享的，不用队列也能直接通信。但**队列 = 管道 + 锁**，多个线程操作同一份数据时可能出现数据不安全，所以为了保证数据安全，线程也可以使用队列。

:::warning[注意]
Python 的 `Queue` 把数据存放在内存中，电脑突然断电数据就会全部丢失，还有其他不少缺陷。实际项目中要用别人开发好的工具，比如 **RabbitMQ、Redis、Kafka** 等，它们支持持久化，生产者和消费者还可以部署在不同的服务器上。
:::

用法回顾（`import queue`）：

```python
import queue

q = queue.Queue()              # 不传 maxsize：源码写明 If maxsize <= 0, the queue size is infinite
q.put(1)
q.put(2, timeout=3)            # put/get 都可以传 timeout 参数
print(q.get())                 # 输出: 1
print(q.get_nowait())          # 输出: 2（取不到立即报错，不阻塞）
q.put_nowait(3)
print(q.full(), q.empty())     # 输出: False False
```

:::note[补充]
前面见过的默认上限 32767 是 `multiprocessing` 模块里的 `Queue`，不是这个 `queue` 模块。`multiprocessing.Queue` 不传 `maxsize` 时上限取自系统信号量的最大值 `SEM_VALUE_MAX`，数值因平台而异。
:::

除了现在用的 `Queue`，`queue` 模块还有两个队列：

**LifoQueue**：LIFO 即 **Last In First Out，后进先出**，和基础课讲的堆栈一样。

```python
import queue

q = queue.LifoQueue()
q.put("A")
q.put("B")
q.put("C")
print(q.get())   # 输出: C（最后放进去的最先拿到）
```

**PriorityQueue**：**优先级队列**，`put` 时传一个元组，第一个元素是表示优先级的数字，**数字越小优先级越高**。

```python
import queue

q = queue.PriorityQueue()
q.put((18, "A"))
q.put((69, "B"))
q.put((36, "C"))
q.put((-1, "D"))
print(q.get())   # 输出: (-1, 'D')
print(q.get())   # 输出: (18, 'A')
```

:::note[补充]
优先级相同时会继续比较元组第二项，若第二项是不可比较的对象（如字典）会报 `TypeError`，常用做法是加一个自增序号：`(优先级, 序号, 数据)`。
:::

## 4.7 池与线程池

### 4.7.1 为什么需要池

现在的服务端每来一个客户端就开一个进程或线程去处理。可不管开线程还是开进程，都要消耗资源，只是线程消耗更小而已。如果同时有 1 万个客户端来连接，服务端就要开 1 万个线程——想都不用想，这不现实。**计算机的硬件资源跟不上软件的消耗**，不可能无限制地开进程或线程。

所以开发程序时，应该**在保证计算机硬件正常工作的前提下，最大限度地利用它**，而不是毫无底线地压榨它。一上来就开 1 万个进程，计算机只能罢工；软件写得再厉害，计算机扛不住、跑不起来，又有什么意义？

**池**：用来在**保证计算机硬件安全的情况下，最大限度地利用计算机资源**。它**降低了程序的运行效率**（不让程序无限制地开进程/线程），但**保证了计算机硬件的安全**，从而让程序能够正常运行。

类比前面学过的**半连接池**：假设服务端的服务能力到了极限，后来的客户端只能在半连接池里等着，半连接池可以限制数量（比如只能再有 5 个等着），再多就进不来了。如果没有限制，1 万个客户端同时连进来，服务端要同时维护 1 万个连接，这些客户端此刻又享受不到服务——与其让他们连着干等，还不如不让他们连接，以减轻服务端压力。同样是降低了效率，但保证了硬件安全。

:::note[补充]
池的另一个好处是**复用**：池中的进程/线程做完任务不销毁，回到池里等下一个任务，省去反复创建、销毁的开销。
:::

### 4.7.2 创建线程池

进程池和线程池都在 `concurrent.futures` 模块中：

- `ThreadPoolExecutor`：线程池
- `ProcessPoolExecutor`：进程池

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

pool = ThreadPoolExecutor(10)   # 线程池里固定 10 个线程
```

点进 `ThreadPoolExecutor` 的源码，有一个参数 `max_workers`（worker 即"干活的人"，在线程池里就是线程），即最大线程数，默认为 `None`。源码里写着：

```python
if max_workers is None:
    max_workers = (os.cpu_count() or 1) * 5
```

`os.cpu_count()` 获取 CPU 个数，后面 `or 1` 的含义：or 运算从左往右判断，只要遇到一个值为真，就直接返回这个值，不再往后判断。

```python
print(3 or 1)   # 输出: 3
print(0 or 1)   # 输出: 1
print(1 or 3)   # 输出: 1（1 的布尔值为 True，不再往后判断）
```

所以 `(os.cpu_count() or 1)` 拿到的就是 CPU 个数（万一获取不到则为 1），再乘以 5。也就是说：**不传参数时，默认开设的线程数 = CPU 个数 × 5**，相当于一个 CPU 干 5 个人的活，CPU 很轻松，压力不会太大。

如果传了值，传的就是池子里的线程数量。比如传 10，池子里就**固定只有 10 个线程**，中途不会出现某个线程被销毁再重新创建的情况——就像开了一家公司，招了 10 个员工，这 10 个员工永远不换。原因是创建线程和销毁线程也要消耗资源，一直固定这 10 个线程，就把中途创建和销毁的资源节省下来了。

:::note[补充]
`× 5` 是 Python 3.5~3.7 的默认值。Python 3.8 起改为 `min(32, (os.cpu_count() or 1) + 4)`，至多 32 个线程。
:::

### 4.7.3 线程池的使用

线程池用法很简单：只需**把任务提交给线程池**，线程池会自动安排一个线程去执行。`pool.submit(task, 参数)` 就是"往线程池中提交任务"。

回顾任务的两种提交方式：

- **同步**：任务提交后原地等待任务的返回结果
- **异步**：任务提交后不等待，继续往下执行

验证 `submit` 是哪一种：

```python
from concurrent.futures import ThreadPoolExecutor
import time

pool = ThreadPoolExecutor(10)

def task(name):
    print(name, "开始")
    time.sleep(3)

if __name__ == "__main__":
    pool.submit(task, "梦泪")   # 往线程池中提交任务
    print("主线程")             # 立马就打印了，没等任务睡完 3 秒
# 输出:
# 梦泪 开始
# 主线程
```

"主线程"立马就打印了，根本没有等任务结束；如果是同步，应该 3 秒后才打印。所以 `submit` 确实是**异步提交**。

再用 `for` 循环提交 50 个任务：

```python
from concurrent.futures import ThreadPoolExecutor
import time

pool = ThreadPoolExecutor(10)

def task(name):
    print(name, "开始")
    time.sleep(3)

if __name__ == "__main__":
    for i in range(50):
        pool.submit(task, i)    # 往池子里提交 50 个任务
# 效果: 每次打印 10 个数字，约 3 秒后再打印下一批 10 个
```

50 个任务是**10 个 10 个**被执行的，因为池子里只有 10 个线程干活。就像房间里有 10 个服务员，门口来了 50 个客人，只能 10 个 10 个来；这 10 个客人体验完，服务员再去门口接下 10 个。

**线程池与信号量的区别**：效果很像，但本质不同。

| | 信号量 | 线程池 |
|---|---|---|
| 本质 | 一把锁 | 一组被复用的线程 |
| 线程由谁创建 | 我们自己创建，想创建多少都可以 | 线程池创建 |
| 控制的是 | 同时**执行**的线程数，其他线程阻塞 | 线程的**数量** |

### 4.7.4 获取异步结果

异步提交不等待返回结果，难道返回结果就不要了？当然还是要的。`submit` 是一个方法，是方法就有返回值——它返回一个 **Future** 对象，表示这次调用。Future 对象有一个 `result` 方法，返回该 Future 对象所代表的调用结果，也就是**异步任务的结果**。

**直接 `result()` 的问题**：

```python
for i in range(50):
    future = pool.submit(task, i)
    print(future.result())   # 每提交一个任务就原地等它的结果
# 效果: 任务一个一个执行，每个任务后面跟着一个 None
```

运行后发现任务变成**一个一个执行**了：原本是异步提交、10 个线程并发执行，调用 `result()` 后程序变成了同步，10 个线程从并发变成了串行。每个任务后面打印的 `None` 就是任务结果——`task` 没写返回值，默认返回 `None`。

如果给 `task` 加上 `return name + 10`，打印的就是加 10 之后的结果，说明 `result()` 拿到的就是任务的返回值。

可是"异步提交一个任务、马上同步拿结果"，异步就没有意义了。思路和 `join` 一样：不是起一个就 join 一个，而是全部起完再逐个 join。

```python
from concurrent.futures import ThreadPoolExecutor
import time

pool = ThreadPoolExecutor(10)

def task(name):
    print(name, "开始")
    time.sleep(3)
    return name + 10

if __name__ == "__main__":
    f_list = []
    for i in range(50):
        future = pool.submit(task, i)
        f_list.append(future)    # 先不拿结果，只保存 Future 对象

    pool.shutdown()              # 关闭线程池，等待池中所有任务运行完毕

    for f in f_list:
        print(f.result())        # 结果按提交顺序输出：10, 11, ..., 59
```

- 这样就不再是串行执行了：50 个任务先提交上去，之后再慢慢等结果
- **结果是有序的**：列表里的 Future 对象是按第 1 个到第 50 个的顺序添加的，取的时候也是先等第 1 个的结果，再等第 2 个……一直到第 50 个
- `pool.shutdown()`：关闭线程池，等待池中所有任务运行完毕。对一个店铺来说，就相当于关门不再接客，已经接待的客人服务完再走

:::tip[技巧]
- `with ThreadPoolExecutor(10) as pool:` 退出代码块时会自动调用 `pool.shutdown()`。
- `as_completed(f_list)` 可以按"谁先完成谁先返回"的顺序迭代 Future 对象，适合不关心提交顺序的场景。
:::

### 4.7.5 异步回调

前面用 `for` 循环一个一个手动 `result()` 获取异步结果，看起来很别扭，不推荐。获取异步任务的返回结果，推荐用**回调机制**（callback）：给每个异步任务绑定一个函数，**一旦该任务有结果，就立刻自动触发这个函数的执行**。

绑定方法：在 `submit` 后面接着点一个 `add_done_callback`——add 是添加，done 是完成，callback 是回调。**传函数名不要加括号**，加括号传的就是回调函数的返回值了。

```python
from concurrent.futures import ThreadPoolExecutor
import time

pool = ThreadPoolExecutor(10)

def task(name):
    print(name, "开始")
    time.sleep(3)
    return name + 10

def callback(res):
    print("callback", res.result())   # res 是 Future 对象，用 result() 拿到任务返回值

if __name__ == "__main__":
    for i in range(50):
        pool.submit(task, i).add_done_callback(callback)   # 不要写成 callback()
```

回调函数收到的参数 `res` 是一个 **Future 对象**，和 `submit` 返回的一样。看 `add_done_callback` 的源码，它在 future 结束时调用回调，调用时写的是 `fn(self)`——这段代码在 `Future` 类里，所以 `self` 就是这个 Future 对象。也就是说：**`add_done_callback` 会自动把 Future 对象本身传给回调函数**，回调函数拿到的就是 `submit` 的返回值，所以可以用 `res.result()` 取结果。

这样一来，哪个任务完成了，就能马上拿到结果，不用再手动循环——这是**获取异步任务结果最理想的方式**。

一共只有三行代码需要掌握，任务函数和回调函数随便写都可以：

```python
from concurrent.futures import ThreadPoolExecutor   # 1. 导入（进程池用 ProcessPoolExecutor）
pool = ThreadPoolExecutor(10)                        # 2. 创建池
# pool.submit(task, i).add_done_callback(callback)   # 3. 提交任务并绑定回调
```

:::note[补充]
线程池中，回调函数由执行任务的那个子线程调用；进程池中，回调函数在**主进程**中执行（子进程只负责计算并把结果传回来）。典型用法：爬虫中进程池/线程池负责下载，回调函数负责解析或保存。
:::

## 4.8 进程池

### 4.8.1 进程池的使用

进程池的使用和线程池**一模一样**，直接把 `ThreadPoolExecutor` 换成 `ProcessPoolExecutor` 即可。

它同样有 `max_workers` 参数，默认为 `None`；`if max_workers is None:` 则 `max_workers = os.cpu_count()`。区别在于：**进程池默认开设的进程数 = CPU 个数**（线程池是 CPU 个数 × 5），因为开进程消耗的资源更多，开太多很"折腾"电脑。

和线程池一样，进程池中的进程也**不会被中途销毁再重新创建**。线程池不好验证这一点，进程池就好验证了：只要进程号一直是固定的那几个就行。

```python
from concurrent.futures import ProcessPoolExecutor
import os
import time

def task(name):
    print(name, os.getpid())   # 打印进程号
    time.sleep(3)
    return name + 10

if __name__ == "__main__":     # Windows 上开进程的代码必须放在这里
    pool = ProcessPoolExecutor(3)
    f_list = []
    for i in range(50):
        f_list.append(pool.submit(task, i))
    pool.shutdown()
    for f in f_list:
        print(f.result())
# 效果: 打印的进程号始终是固定的 3 个（顺序可能不同）
```

:::warning[注意]
Mac 系统不写 `if __name__ == "__main__":` 也没问题；但 **Windows 上开进程的代码必须放在 main 判断下面**，否则会报错，所以创建进程池、提交任务都要在 main 下面做。
:::

:::note[补充]
进程池中的任务函数和参数需要能被 `pickle` 序列化（要在进程间传递），所以不能提交 lambda 或局部函数；进程池适合计算密集型任务。
:::

### 4.8.2 进程池的回调

进程池绑定回调的写法和线程池完全一致，只是回调函数在**主进程**中执行：

```python
from concurrent.futures import ProcessPoolExecutor
import os

def task(name):
    return os.getpid(), name + 10    # 把子进程号和结果一起返回

def callback(res):
    pid, result = res.result()       # 回调函数在主进程中执行
    print("回调收到:", pid, result)

if __name__ == "__main__":
    pool = ProcessPoolExecutor(3)
    for i in range(6):
        pool.submit(task, i).add_done_callback(callback)
    pool.shutdown()                  # 等待所有任务及回调完成
    print("全部回调完成")
# 输出（进程号固定为 3 个，顺序可能不同）:
# 回调收到: 27396 10
# 回调收到: 44280 11
# 回调收到: 48376 12
# 回调收到: 27396 13
# 回调收到: 44280 14
# 回调收到: 48376 15
# 全部回调完成
```

## 本章小结

- 进程是资源单位，线程是执行单位；每个进程自带一个主线程；开线程不用申请内存、不用拷贝代码，开销小，同一进程内数据共享
- `threading.Thread` 两种创建方式与 `Process` 一致；线程 `start()` 后几乎立刻运行；常用 `join()`、`current_thread().name`、`active_count()`
- 多线程 TCP 并发：主线程只负责 `accept` 接客，每个连接开一个线程执行通信循环；"来一个开一个"在客户端多时会耗尽资源，所以要引入池
- 主线程代码运行完毕后要等所有非守护线程结束才真正结束；守护线程在主线程**结束**时陪葬
- 多线程修改共享数据会错乱，用 `Lock` 加锁（`acquire/release` 或 `with`）把并发变串行
- GIL 是 CPython 独有的全局解释器锁，因内存管理（垃圾回收）不是线程安全而存在；它保证解释器级别的数据安全，导致同一进程下多线程无法利用多核；遇 IO 会释放 GIL，所以用户数据仍需自己加锁
- 多核下：计算密集型用多进程，IO 密集型用多线程；实际开发的程序 90% 以上是 IO 密集型，常用多进程 + 多线程组合
- 死锁：多个线程各自拿着对方需要的锁又互相等待，程序夯住；互斥锁要谨慎使用
- `RLock` 递归锁可被同一线程连续获取，内部计数归零后其他线程才能抢；用 `mutex1 = mutex2 = RLock()` 让两个名字指向同一把锁
- `Semaphore(n)` 像有 n 个车位的停车场，用于限流；`Event` 用 `set()` / `wait()` 让子线程之间等待信号
- `queue` 模块：`Queue`（先进先出）、`LifoQueue`（后进先出）、`PriorityQueue`（数字越小优先级越高）；仅适合本地测试，项目中用 RabbitMQ、Redis、Kafka 等
- 池在保证硬件安全的前提下最大限度利用资源：**降低了效率，保证了硬件安全**，池中的进程/线程固定不变、反复复用
- `concurrent.futures` 中 `ThreadPoolExecutor` / `ProcessPoolExecutor` 用法一致；不传参数时，线程池默认 CPU 个数 × 5（Python 3.8 起改为最多 32 个），进程池默认 CPU 个数
- `submit` 是异步提交，返回 `Future` 对象；`future.result()` 会原地等待，提交后立即调用会让异步变串行；推荐用 `add_done_callback(callback)` 异步回调，回调收到的是 Future 对象本身
- Windows 上使用进程池必须写在 `if __name__ == "__main__":` 下

<details><summary>参考答案</summary>

1. 操作系统是工厂，进程是车间，线程是流水线：车间（进程）提供原材料、电力等资源，真正干活的是流水线（线程），所以进程是资源单位、线程是执行单位，每个进程至少自带一个线程。创建进程需要申请内存空间、拷贝代码；在进程内创建线程不需要这两步，直接使用所在进程的资源，所以开销小得多。

2. 输出为：任务1开始、任务2开始、主线程、任务2结束。主线程代码运行完后要等非守护线程 t2 结束（2 秒）才结束；主线程结束时 t1 还没睡够 3 秒，作为守护线程跟着陪葬，"任务1结束"不会打印。

3. GIL 只保证解释器级别的数据安全；线程进入 IO（如 `sleep`）时会自动释放 GIL，其他线程就能拿到同一个旧值，导致业务数据错乱，所以要自定义互斥锁。加锁后线程遇到 IO 时：GIL 被释放，但自定义锁仍被该线程持有，其他线程虽能抢到 GIL，却会卡在 `acquire()` 处，保证同一时刻只有一个线程操作数据。

4. 纯计算：多进程约 10 秒多一点（10 个核同时计算），多线程约 100 秒（同一进程下的线程无法利用多核）。纯 IO：两者耗时差不多，都约 10 秒多，但多线程更节省资源，因此 IO 密集型用多线程。

from threading import Thread, Semaphore
import time

sp = Semaphore(2)   # 2 个窗口

    with sp:

6. `submit` 是异步提交，但紧接着调用 `result()` 会原地等待该任务的结果，于是每个任务都要等上一个完成后才能提交，异步变成了同步（串行）。应先把 Future 对象存进列表，全部提交后（可先 `pool.shutdown()`）再逐个 `result()`，或者用 `add_done_callback` 绑定回调。

7.
```text
from concurrent.futures import ThreadPoolExecutor

pool = ThreadPoolExecutor(3)

def task(n):
    return n * n

if __name__ == "__main__":
    f_list = [pool.submit(task, i) for i in range(10)]   # 先全部提交
    pool.shutdown()                                      # 等待全部完成
    for f in f_list:
        print(f.result())                                # 按提交顺序：0 1 4 9 ... 81
```
